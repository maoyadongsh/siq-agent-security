# Grant 列表一致读回（Issue #53）

## 合同

`GET /v1/grants` 成功时保持既有 `grants`、`state_revisions` JSON 结构。每个 Grant 的内容及 revision 必须在同一次存储读回中取得；不能先列出正文，再逐项读取另一个时刻的 revision。成功空列表仍是空数组及空 revision 对象。

服务拥有既有跨进程 Writer 时，同一状态目录内的合作 Grant 写入（完整提交、恢复、普通版本发布和 CAS 发布）与列表快照使用共享的进程内读写门禁；不同 Store 对象不能绕过它。正在进行或排队的写入使列表立即返回 `503 {"error":"grants_busy"}`，并带 `Retry-After: 1`，不返回旧授权、局部结果或成功空列表。不按长期存在的 serve.lock、文件时间或 prepare 文件年龄猜测写入是否仍活跃；不同状态目录互不造成 busy。

只有内存门禁当前存在合作写者才能产生 `grants_busy`。取得快照门禁后，孤立未完成提交、损坏正文、错误 commit 摘要或不可读取状态仍返回原有 `500 {"error":"store unreadable"}`。GET 不启动恢复、不写日志或状态、不创建锁文件、不覆盖/删除记录。永久错误不降级为可重试 busy。已有 GetGrantWithSeq、授权选择器及 receipt 的未完成撤销拒绝语义保持不变。

快照期间阻止同状态目录内的合作写者发布新 Grant，使整张列表与 revision 在一个读临界区中一致；跨进程修改仍依赖现有单 Writer 协议，不将此进程内门禁宣传为防同用户外部篡改的文件系统隔离。门禁以已验证原始状态根的规范绝对路径共享，Windows 对大小写别名保守共用门禁；不改磁盘格式、签名字节或授权语义。

UI 只对精确的 `503/grants_busy` 显示授权更新中的提示，保留已有失败状态及刷新入口/待办轮询，不把旧行标作最新，也不自动重试批准、撤销等写操作。其他错误继续沿现有错误处理显示。

## 必需验证

- approve、revoke 在 prepared 与 grant 两个真实发布边界暂停时，GET 返回 503、固定错误及 Retry-After，响应不含授权或 revision；释放后取得精确新版本。
- 暂停撤销期间及提交后，授权选择器不能重新选中旧授权。
- 提交退出但遗留 prepare、损坏最新版本、错误 done 摘要均保持 500，GET 不恢复或改变文件。
- 首个新 Grant 尚未发布时不能返回成功空列表；不同状态目录不被误标 busy。
- 同目录不同 Store、CommitGrantFrom、恢复及普通/CAS Grant 发布共用门禁。读回返回的所有 revision 与该次 Grant 正文一一对应。
- 读操作前后的不可变文件及审计没有额外变化；原有并发派生、恢复、损坏状态拒绝和安全回归仍需通过。

实现与验证进度分别记录；本规格本身不证明测试通过。
