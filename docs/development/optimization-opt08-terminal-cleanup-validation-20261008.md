# OPT-08/10：原生宿主终止确认修复与真实业务复核

日期：2026-10-08。环境：DGX Spark＋本地 Qwen＋Hermes 原生 Skill＋OpenShell＋智能分析助手。

本批完成四轮真实端点启动／取消诊断，并修复原生宿主终止操作在确认暂时不可用时立即失败的问题。修复后，**同一业务候选的三次真实模型撤权验证均通过**。OPT-08、OPT-10 仍在实施；本批不代表完整权限矩阵或最终发行验收完成。

## 1. 问题与修复范围

此前 v834、v837 撤销业务权限后，监管日志依次出现 `guard_tick / run_guard`、`close_native / unclassified`，并以 `supervisor_containment_failed` 退出；随后恢复流程完成资源回收。最终资源不存在与首次终止确认成功是两个不同事实，旧结果继续保留。

业务提交 `7e52689` 为 `RequestNative.close()` 增加了原进程、原 handle 的有界 `stop` 重试。宿主控制合同已经允许原 handle 的终止操作；没有重试 `start` 或 `renew`，没有放宽授权、端点身份或子进程归属校验。每次控制调用仍验证私有配置、Unix 对端凭据、pidfd 和完整响应绑定。

- 只有经过控制客户端核验的 `closed` 响应才确认终止。
- 最多 17 次尝试、8 秒重试窗口，间隔最多 0.5 秒。单次调用原有 30 秒上限仍适用，最坏等待约 38 秒，不能称为严格 8 秒结束。
- 业务授权过期后仍可终止原会话；跨进程调用拒绝。
- 持续错误、超时或未知异常不被当作清理成功；失败仍进入原有 containment。

两个新增用例在旧实现上失败，修复后相关原生请求、私有控制传输和监管器 **86 项测试通过**，Ruff 和差异检查通过。测试覆盖首次终止确认失败后恢复、持续失败的边界、授权过期、意外异常和跨进程调用。组件中的临时失败是显式注入，不能据此断言旧现场的底层原因已经完全复现。
