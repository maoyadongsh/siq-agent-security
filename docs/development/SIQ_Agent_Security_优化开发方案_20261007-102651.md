## 1. 执行摘要

本次优化围绕一个核心结果展开：在明确的信任边界和真实接入链路内，合法 Agent／Skill 能完成用户授权的工作；未授权、授权失效、身份错配或保护服务异常时，危险动作不会产生实际副作用，并能够解释和复核处理结果。

实施采用四层顺序：

1. **安全正确性与恢复可靠性**：修复已复现的回执链竞争，补齐生产身份隔离、扫描资源预算、错误脱敏、回滚持久化与 pending 幂等。
2. **Agent／Skill 真实权限闭环**：将历史多候选证据收敛为同版本回归，补日常入口 Skill 上下文绑定，并完善企业 OpenShell 行为验证。
3. **交付与纵深防护**：完善连接器可信路径、钩子完整性、交付入口安全头及 Windows／macOS 同候选原生验收。
4. **研究候选**：Host Sensor、YARA、受控动态分析先做边界与收益评估，不作为前三层完成的默认前置条件。

本方案不追求新增能力数量。每个改动必须回答：解决什么可复现问题、保护哪条权限边界、用什么观察证明有效、失败后如何恢复。

## 3. 目标、非目标与安全不变量

### 3.1 产品目标

- 权限以可信用户授权和后端事实为准，模型不能自行获得或扩大权限。
- Agent、安装实例、Skill、会话、任务和资源边界能够在执行前关联并核验。
- 撤权、过期、内容漂移、身份错配和保护服务失联产生可解释的拒绝或中止。
- 合法任务的完成质量与安全结果同时记录，避免“全部阻断即安全”的错误指标。
- 回执、审计与实际效果能够相互关联，错误、未知和未观测不冒充成功。
- 部署、升级、重启、故障恢复后仍维持相同边界。

### 3.2 本期非目标

- 不把 `desktop-same-uid` 宣称为对同一 OS 用户的恶意进程进行通用隔离。
- 不以本轮修复自动上调 `managed-linux`、平台支持矩阵或正式发行包验收状态。
- 不引入全新 EDR 产品线，也不要求先实现 Host Sensor 才能修复现有问题。
- 不把 YARA 命中或模型判断作为权限签发依据。
- 不执行被扫描的 Skill 来替代现有静态分析；动态研究如立项必须使用独立分析链。
- 不覆盖历史失败、冻结签名、原始分母、既有发行制品或其他开发者未提交工作。

### 3.3 必须保持的约束

1. 租户、用户、主体和权限来自已验证身份；对象定位与授权规则保持现有合同。
2. 私钥、token、配对码、完整私有配置不进入日志、报告、公开证据和前端持久化。
3. 高风险写入保留审计要求；不能通过“错误降级”绕开授权或审计。
4. `declared`、`observed`、`effective` 与验证等级保持区分。
5. `block` 模式下裁决服务不可用仍拒绝；不得改变 `warn/audit_only` 的既有普通策略语义或放宽必需 Authority 的独立拒绝。
6. 宿主钩子保持薄适配，不持有签名私钥、不复制规则裁决逻辑。
7. 已签名回执追加保存；恢复和去重不能重写旧链或补造历史决定。
8. 跨仓库只通过版本化 API、事件或宿主公开接口连接，不读写兄弟数据库。

## 6. 第一批：安全正确性与恢复可靠性

### OPT-00：冻结基线、对齐旧任务与复现清单

**范围**：文档与本地实施台账。

1. 从实施时最新 `main` 建立隔离工作区；记录提交、工作树差异、工具版本和相关运行环境。
2. 将本方案与 SEC-F01–SEC-F10、企业收口工作包、平台待办逐项映射为“已覆盖、部分覆盖、新增、待确认”。已覆盖项引用现有任务，不复制实现。
3. 每项发现记录调用路径、触发条件、受影响主体、实际后果和证据强度。
4. 在修复前冻结最小负向用例；无法复现时保留调查状态，不为符合原报告而制造修复。
5. 本机 `var/advice-review-20261007/` 中的 H1 overlay 与日志可作为起点，后续必须形成仓库内可重复的回归测试；本地路径不是跨机器交付依赖。

**验收**：每个任务有唯一归属、明确状态、基线和验收入口；旧草稿及历史证据无改写。

### OPT-01：回执链并发一致性

**代码范围**：`apps/agentshield/internal/receipt/chain.go`、同目录 `engine.go`、`internal/server/server.go` 及对应测试。

**问题**：Engine 的互斥锁并未覆盖服务器直接调用 `Chain.Head()` 的读取；已复现 `seq/head` 竞争。

**实现步骤**：

1. 列出 Chain 的全部读写入口，包含追加、Head、检查点发布、读取及初始化配置。
2. 优先由 Chain 自身统一保护可变状态；规定锁顺序与是否允许嵌套，防止 Engine 锁与 Chain 锁形成死锁。
3. `seq/head` 必须作为一致快照读取；不能只把两个字段分别原子化。
4. 追加串行化必须覆盖前序摘要选取到持久化及内存发布。明确文件写入成功、检查点失败时的已提交状态，避免调用方重试造成重复。
5. 不改变既有回执字节、签名算法和历史链格式；若调整错误返回语义，先更新规格。

**验收**：

- 同一聚焦用例在基线上触发 race，在修复后 `go test -race` 通过。
- 并发状态读取与写入获得合法的序号／摘要组合；链完整验签通过。
- 覆盖多个追加请求、写入失败、HEAD hint 失败、检查点失败和重启恢复。
- 状态查询不死锁；增加锁后记录吞吐与查询延迟变化，不以性能理由取消正确性控制。

**回退**：回退代码需维持已写回执可读取；不得通过删除链文件恢复。

### OPT-02：生产构建与身份边界

**代码范围**：`apps/web/src/api/client.ts`、`apps/web/vite.config.ts`、构建脚本、`apps/control-api/app/security.py`、配置检查和相关测试。

**设计**：前端构建防误配置与后端身份验证是两道独立防线。

1. 开发身份头必须同时满足明确开发开关和非生产环境；推荐表达式为 `import.meta.env.DEV && VITE_DEV_MODE === 'true'`，或等价且经测试的策略。
2. 构建阶段检测误开启开发身份注入。缺省、空值和显式 false 的行为需要定义，不能机械要求所有环境都必须手工设置 false。
3. 覆盖普通构建、本地嵌入构建和自定义 mode；防止某条打包路径绕过约束。
4. 后端在生产配置中拒绝仅携带 `X-Dev-*` 的请求；有效 JWT 与伪造开发头并存时不得改变 JWT 的租户或角色。
5. 保持开发联调可用，开发便捷配置不成为生产权限来源。

**验收**：生产产物请求不注入开发身份；恶意开发头无法替换身份；配置误用有明确失败提示；开发环境正向测试通过。不能仅搜索产物中是否含某个字符串来代替行为测试。

### OPT-03：威胁扫描资源预算与限流

**代码范围**：`apps/control-api/app/routers/threat.py`、`rate_limit.py`、配置、请求模型、`threat_analysis.py` 和扫描测试。

1. 保留现有身份验证、对象定位、权限、内容绑定和大小限制。
2. 增加按已验证 tenant 与 actor 的配额，并设置租户汇总、全局并发上限；单 actor 限制不能被创建多个身份轻易稀释。
3. 明确限流状态码、`Retry-After`、审计/指标以及失败不产生半完成 Finding 的语义。
4. 在昂贵分析前执行预算检查；请求体和解码阶段也要有大小边界。
5. 评估现有限流器的键数量、过期清理与多 worker 限制，防止限流器自身无界增长。
6. 单进程限制应如实标注；多副本部署需共享配额或明确总预算。不能把进程内测试写成集群限流证明。
7. 用固定语料测普通样本、深层语法、长字符串、最大内容、并发请求的 CPU、内存及治理 API 延迟。
8. 实测后冻结配额、并发和超时默认值，记录硬件与样本摘要；本文件不编造最佳 QPS。

**验收**：配额内正常扫描；超额可预期拒绝；租户隔离；突发结束后恢复；治理端点不被扫描持续饿死；请求失败不制造成功扫描记录。

**边界**：线程或异步等待超时不保证停止底层 CPU 工作。需要强制 CPU/内存预算时转入 OPT-14。

### OPT-04：错误、输入与列表行为收敛

**代码范围**：控制面 `routers/policies.py`、`routers/bindings.py`、安全错误工具；本地 `server.go`、`ledger_http.go`。

- 列出仍将异常原文返回 HTTP 的路径，统一稳定错误码、摘要和可关联请求标识；诊断日志本身也要脱敏。
- 已使用 `error_reference` 的路径保持不变；受控业务错误与未知异常分别处理，避免所有错误变成不可操作的“失败”。
- 对 asset action 等状态修改入口明确空 body、畸形 JSON、超大 body 的合同；不允许解析失败后按零值继续写入。
- 盘点数据读取失败不得显示为“扫描成功且没有资产”；使用明确失败或有标记的部分结果。
- pending 补录等 best-effort 工作失败需可观察、可重试，但不得错误放行本次未授权动作。
- 列表参数明确范围，建议 `1 <= limit <= 200`；超界按统一合同拒绝或截断。若保留截断，返回机器可读元数据。
- 同时在生产 PostgreSQL 和适用的开发数据库中验证，避免只覆盖 SQLite 行为。

**验收**：植入路径、凭据形态和私有配置片段的异常不外泄；非法输入无副作用；分页边界正确；错误不会变成“无风险”或“已完成”。

### OPT-05：OpenShell 操作持久化与后端绑定

**代码范围**：`operation_registry.py`、`cli_backend.py`、`routers/policies.py`、部署模型、Alembic 迁移及相关合同。

**问题范围**：重启、跨 worker、超过 256 条记录淘汰后均可能找不到操作；当前环境变量也可能选择与原部署不同的回滚分支。

**建议记录**：操作 ID、租户／环境／binding／deployment、后端类型、目标身份、网关指纹、前置 revision/digest、应用 revision/digest、受保护的精确前置快照或其持久引用、状态、创建时间与并发版本。字段以合同评审结果为准。

**实施步骤**：

1. 区分用于提速的进程缓存和可恢复的持久事实源。
2. 在外部变更前持久化操作意图；外部写入和本地数据库不能伪装成一个原子事务。
3. 建模 `prepared/applying/applied/verification_failed/rollback_pending/rolled_back/unknown` 等所需状态，统一与现有部署状态的映射，不直接堆叠第二套矛盾状态。
4. 外部写入成功但本地提交失败时，通过精确读回与操作身份恢复；不盲目重试写入。
5. 回滚选择来自原部署记录，当前配置仅用于重新建立受信连接；不一致时拒绝或进入恢复流程。
6. 回滚前重新检查租户、活体授权链、binding、网关身份、当前 revision 和摘要；持久记录不能成为绕过重新授权的凭证。
7. 跨进程并发采用适用的数据库约束／锁及后端版本检查。若后端没有原子 CAS，明确并发窗口，不能把进程锁升级描述为全局保护。
8. 前置快照不得公开返回；按敏感配置处理，不保存无关 provider 密钥。
9. 历史部署缺记录时安全拒绝自动回滚，给出明确恢复路径，不根据调用者提交的快照重建可信操作。

**验收**：重启后精确回滚、不同 worker 接续、超过缓存容量仍可回滚、重复请求幂等、并发回滚互斥、策略漂移拒绝、后端切换拒绝、数据库和外部命令故障恢复、未授权与跨租户拒绝。

**迁移与回退**：采用兼容的增量迁移；禁止降级时删除仍用于恢复的操作数据。回退软件后必须说明哪些新状态无法处理。

### OPT-06：pending 提升幂等与审计完整性

**代码范围**：`internal/pending/promote.go`、`internal/receipt/engine.go`、回执查询与校验、既有 v1/v2 合同。

1. 定义稳定的原始事件身份，区分重复提交同一事件和内容相同的两个独立事件；不能仅用可能碰撞的短 ReceiptID 推断相同。
2. 保持 v1 与 v2 的观测语义，尤其 `local_failure` 和 unknown 不转成在线授权决定。
3. 补录前查找已提交事件；回执落盘后游标丢失时能够识别并继续推进。
4. 去重索引若使用缓存必须可由不可变日志恢复，并与单写者约束协调。
5. 不把旧链出现重复标识简单升级成“历史签名无效”；新增语义校验、历史异常标记与签名校验分别报告。

**故障注入点**：追加前、追加成功后游标写入前、游标临时文件写入后、替换后、重启、两个提升请求并发。

**验收**：同一原始事件不新增重复语义记录，游标正确恢复，独立事件不丢失，链可验签，v1/v2 夹具兼容，故障不改变拒绝事实。

### OPT-07：静态策略语义与部署入口一致性

**代码范围**：`policy_compiler.py`、`cli_backend.py`、部署及 preview/submission 路由、`apps/web/src/api/client.ts`。

**静态策略**：

- 为字段省略、null、空对象、空列表和显式删除建立语义表；特别区分 patch 与完整替换。
- 验证缩短 allow 集、删除字段、仅更新网络、未知扩展字段保留及 generation 判断。
- 已有“网络更新保留静态段”的测试应继续成立。不能将省略字段统一解释为删除。
- 静态变化需要重建而当前后端不能执行时明确拒绝，不返回动态更新成功。

**部署入口**：

- 枚举旧 `/deployments`、preview、submission、batch、CLI/Edge 等实际可达入口。
- 对同一主体执行相同未授权、审批失效、binding 吊销、目标漂移和重复执行反例。
- 确认旧入口是否属于支持中的 API；如需关闭，先做版本和迁移说明，不能仅删除前端函数。
- 未被调用的 `createDeployment` 可作为清理项，但不将清理结果当成服务端越权修复。

**验收**：静态意图不静默丢失；同类动作在所有入口遵守同一后端授权不变量；明确哪些入口要求预览摘要及其合同依据。

## 7. 第二批：Agent／Skill 真实权限闭环

### OPT-08：日常业务入口的可信 Skill 上下文

**主场景**：DGX Spark＋Hermes＋OpenShell＋`siq-research-engine` 智能分析助手。

**基线限制**：现有 Agent 证据来自日常业务入口；Skill 证据来自真实安装和原生加载的专属验收入口，并使用显式上下文绑定。不能据此认定日常入口已自动识别任意 Skill 切换。

**实施步骤**：

1. 从真实入口追踪用户授权 → 业务范围 → Agent/run/session → 原生 Skill 加载 → 工具分发 → SIQ 裁决 → 执行 → 效果观察。
2. 明确由可信宿主提供安装实例和 Skill 上下文，模型文字不能指定或替换其身份。
3. 绑定安装摘要、Grant、Agent、session、task、资源范围和 SEC 生命周期；执行前重新核验必要状态。
4. 处理无 Skill、单 Skill、嵌套调用、切换和并发上下文。宿主不提供足够事实时标为未知，并按所需 Authority 规则拒绝，不能推测一个已授权 Skill。
5. 覆盖安装升级、内容漂移、SEC 撤销、业务权限撤销、任务结束和租约失效。
6. 若任务确需修改独立业务仓库或 Hermes，分别建变更清单、验证与提交；不在 SIQ 仓库复制业务鉴权。
7. 测试阶段可保留受控同步器；日常产品验收不能仍依赖操作者手工选择技能却宣称自动归因。

**验收**：通过日常入口加载两个不同权限的真实 Skill；A 的上下文不能借用 B 的 Grant；切换、并发、撤权和漂移均有正负向结果；实际文件／网络效果与决定对应。

### OPT-09：企业 OpenShell 行为证据闭环

**代码范围**：`enforcement_probe.py`、`probe_channel.py`、`cli_backend.py`、部署状态及审计；关联前端结果展示。

**前置**：OPT-05 操作身份与恢复语义稳定；真实目标可控；先冻结探针协议。

1. 明确只读验证与主动探针的权限、目标和副作用范围，使用固定模板与受控接收端。
2. 探针绑定目标、网关指纹、策略 revision/digest、操作身份、时间窗口及执行程序身份。
3. 核验允许组、拒绝组和可达性对照组，满足现有校验器的样本要求；不能把 DNS 失败、服务停止或超时一概算作策略阻断。
4. 在真实 OpenShell 目标确认 binary 路径归因前提，并记录镜像和工具摘要。
5. 探针前后复核策略未变化；检测过期、重放、跨目标和伪造证据。
6. 优先作为持久部署操作的独立验证阶段，明确 pending、失败、未知、可重试及超时；不要让长探针阻塞数据库事务。
7. 只有校验器接受的证据才能提升等级；UI 同时呈现部署状态、验证等级、验证范围和时间。
8. 未验证的 IPv6、重定向、替代程序路径等单列缺口，不被一次成功探针继承为通过。

**验收**：真实三臂对照成功；错误摘要、revision、目标、指纹、过期及重放被拒；探针服务故障保持未验证；策略变更使旧验证失效；恢复不重复产生不受控网络访问。

**等级边界**：即使某个部署获得 `enforcement_verified`，结论仍限定于该目标、策略和探针覆盖范围，不代表全部工具与所有网络路径均被证明安全。

### OPT-10：同候选真实业务回归与分层对照

**目标**：将历史多批次能力证据收敛成一套可独立复查的最终候选验收。

**候选清单**必须包含 SIQ、业务 API、Hermes、适配器、OpenShell/镜像、Skill 安装内容、策略和协议摘要。一个仓库的 Git SHA 不能替代整个运行栈身份；未提交补丁必须单独登记。

| 用例族 | 合法正向 | 必需反例 | 独立观察 |
| --- | --- | --- | --- |
| Agent 读取 | 授权公司／项目读取完成 | 跨公司、未授权目录、路径别名 | 合成 canary 是否被读取或输出 |
| Agent 写入 | 批准窄目录写入 | 只读 Grant、兄弟目录、资源替换 | 文件存在、字节、摘要与写入时间 |
| Skill 权限 | 已安装且已授权 Skill 完成任务 | SEC 错配、其他 Skill 借权、上下文缺失 | 加载事实、决定与文件效果 |
| 生命周期 | 合法续期／更新后继续 | 撤权、到期、旧 SEC、安装漂移 | 撤权返回后受控下一步的实际效果 |
| 故障恢复 | 服务恢复后合法重试 | relay／裁决服务失联、重启、重复提交 | 不产生越权副作用、不重复高风险执行 |
| 工具入口 | 已支持工具调用正确执行 | 未映射工具、别名、嵌套与替代入口 | 实际被执行的工具和归属 |
| 正常任务效用 | 用户任务完成且结果可读 | 错误全阻断、授权后仍无法完成 | 任务成功、工具完成与交付质量分列 |

**四臂对照**按用例适用性设置：未接入防护基线、仅 SIQ、仅 OpenShell、SIQ＋OpenShell。只在一次性环境和合成资产上进行；若某臂无法保留相同运行语义，标为不可比，不强行给出增量百分比。

- 选择 OpenShell 已允许的目录测试 SIQ 窄授权，证明 SIQ 的额外约束。
- 选择超出已接入工具门禁的受控路径，测量适用 OS 边界；不声称 SIQ 独自阻断所有旁路。
- 固定任务、资料、模型配置和版本；模型随机性、调用失败和重试分别登记。
- 建议确定性权限用例每例至少 3 次独立执行，随机模型任务的重复数在试点后预注册。该数量是重复性起点，不提供普遍统计保证。
- 所有计划单元记录 pass/fail/partial/blocked/skipped；阻断但没有真实尝试的用例不能算一次成功防御。
- 一旦修复候选变化，相关测试失效并重跑；影响公共授权链时重跑整套核心权限矩阵。

**验收**：冻结最终候选完成全部必需单元；未授权副作用观察数为 0；全部强制正向用例可完成；缺失观察不能计入 0；独立验证器核对决定、签名、上下文与效果。任何关键用例失败都阻止本批“完成”结论，但历史失败照常保留。

## 8. 第三批：交付与纵深防护

### OPT-11：连接器可信解析与执行

**范围**：`edge/agent/connector.go` 及部署配置、安装工具和测试。

- 保留受管模式与开发模式的明确差异；受管模式使用显式可信位置，不静默回退 PATH。
- 检查二进制及父目录的权限、所有权、链接与可替换性；仅绝对路径不足以建立可信性。
- 按平台评估摘要／签名绑定和执行前替换窗口；不要承诺仅一次 hash 检查即可消除 TOCTOU。
- 保持官方连接器 allowlist、受控环境、超时与输出限制，不额外传递 Edge 凭据。
- 配置迁移错误要可操作，不能导致已安装设备无解释地失联。

**验收**：PATH 投毒、可写父目录、链接替换、错误摘要／签名被拒；合法升级与开发显式配置正常；按 Linux、Windows、macOS 分别记录证据。

### OPT-12：钩子完整性与可信安装

**范围**：`adapters/runtime/`、安装／卸载工具、可信清单与运行诊断。

- 在安装和升级时校验完整制品，记录受保护的版本／摘要身份。
- 检查可信宿主是否支持从受保护位置加载钩子；校验方与预期摘要不能完全位于攻击者可替换的同一目录。
- 增加独立诊断与漂移告警；诊断发现异常不等于已经阻断，必须测试其执行后果。
- 保留安装前备份、完整卸载、共享配置保留和异常恢复。
- 若强保护依赖不同 UID 或只读挂载，单独说明部署要求；不自动升级现有桌面信任档位。

**验收**：篡改、删钩子、替换清单、升级中断和卸载恢复分别测试；对可完全控制宿主的攻击者保留边界，不把自校验视为独立信任根。

### OPT-13：交付入口安全头与浏览器行为

**范围**：企业 Nginx、Go 本地静态服务、相关代理及浏览器测试。

- 保留 `apps/web/security-headers.inc` 已有 CSP，不新增与现有配置矛盾的 HTML meta 策略。
- 对实际响应检查 HTML、资源、SPA 回退和错误页面；代理链可能覆盖或遗漏响应头。
- 核对 CSP、frame 限制、MIME、Referrer、缓存与 CORS/Origin；本地 loopback 的 Host 校验单独保留。
- 逐步收紧策略前运行真实 UI 正向测试，不以破坏样式或认证流程作为安全收益。

**验收**：不同交付入口行为有证据；适用注入／跨站负向被拒；普通管理流程可完成；未测完整 DNS rebinding 链不得标记为已防御实证。

### OPT-14：扫描进程隔离

**触发条件**：OPT-03 显示同步分析无法满足资源预算，或产品要求不可信复杂样本不能影响治理进程。

- 先写 ADR，明确独立 worker、队列上限、取消、超时杀停、内存限制、并发和重试策略。
- Worker 只接收最小必要输入，不持有治理管理员凭据；限制文件系统和网络访问。
- 扫描结果带规则版本、输入摘要和任务身份，控制面核对后按既有事务生成 Finding。
- worker 崩溃返回分析失败或未知，不返回 clean；不得让失败样本无限重试耗尽队列。

**验收**：资源耗尽和进程崩溃不拖垮治理接口；输入串租户、结果错配、重复消费和超时均被正确处理。

### OPT-15：跨平台验收与有界清理

- 在最终候选上分别验证 Windows WorkBuddy、macOS 对应宿主及 Linux DGX Spark 安装、启动、授权、越权拒绝、升级和恢复。
- 区分交叉编译、源码单测、原生 CLI、真实桌面业务、发行包验签；缺机器记 blocked，不借用其他 OS 结果。
- ReceiptID、线性查询、生产 assert、请求超限状态码等逐项做影响分析和聚焦测试；不为整洁修改密码学格式。
- 高熵 token 的哈希存储与密码存储分开讨论，不机械加入盐或更换算法。
- 依赖评估以实际锁文件和可复现安装为准，不因声明范围存在就认定“没有锁版本”。
- 只删除证明确实无调用方或被替代的代码；冻结材料保留。

**验收**：每个平台有精确候选、安装包身份、宿主版本和结果；清理有行为等价证据，没有为消除告警扩大权限。

| 任务 | 研究内容 | 立项前必须回答 | 当前决议 |

| RES-01 | Host Sensor／宿主强制执行 | 目标攻击者是谁；只观察还是强制；如何把进程／容器映射到 Agent/Skill；权限与性能成本；Linux 以外如何交付 | 保留研究，不进入本期完成条件 |

## 10. 测评指标与结论规则

| 指标 | 计算／记录方式 | 不能替代的结论 |
| --- | --- | --- |
| 未授权副作用 | 具备完整观察的拒绝用例中，实际越权读取／写入／外传事件数 | 无日志不能当作无副作用 |
| 合法任务成功率 | 完成全部预注册交付条件的合法任务数／已执行合法任务数 | 工具返回 success 不等于用户任务完成 |
| 拒绝正确性 | 有效攻击尝试中正确拒绝且无副作用的比例；列出样本类别 | 没有发起工具调用不能计成功防御 |
| 证据完整率 | 同时具备身份、授权、决定、必要观察及可复核效果的单元比例 | 签名有效不代表实际执行发生 |
| 恢复可靠性 | 按故障点分别记录恢复成功、重复副作用、丢事件 | 一次正常重启不替代崩溃窗口测试 |
| 性能 | 固定负载的 p50/p95/p99、CPU、峰值内存、超时与队列长度 | 不同硬件或样本结果不能直接相减 |
| 增量效果 | 同条件对照中的拒绝、实际副作用和合法效用变化 | 联合组结果不自动全部归因于 SIQ |

试点用于确定时间预算、重复数和性能阈值；正式测前冻结。样本量小或非独立时不推断总体安全率，不合并不同版本、不同来源和不同测试层次的分母。

## 12. 开发、验证与合并门禁

### 12.1 每个任务的执行流程

1. 读适用 `AGENTS.md`、规格、合同和原测试，刷新代码位置。
2. 更新任务状态及最小复现；先确认旧行为确实失败或缺失。
3. 行为变化先回写规格；合同变化先更新版本、生产方和消费方。
4. 在隔离分支实现最小修改，不夹带依赖升级、目录重排和无关格式化。
5. 运行聚焦正负向、并发／故障测试，再运行模块要求的验证。
6. 检查副作用、密钥、原始数据、生成资源及历史证据是否进入差异。
7. 形成可审阅 PR；在最终提交上检查 CI，不能引用旧提交绿灯。
8. 合并后读回主线状态；涉及制品或原生行为的任务继续对应验收，不能以合并代替交付。

### 12.2 验证命令与适用范围

从各模块目录执行，工具版本以仓库配置为准：

```bash
# apps/agentshield：运行时改动
# gofmt -l 必须无输出；不能只看退出码
gofmt -l .
go vet ./...
go test ./...
go test -race ./internal/receipt ./internal/pending ./internal/server

# apps/control-api：控制面改动
uv sync --dev
uv run ruff check app
uv run pytest

# apps/web：前端改动
npm ci
npm test
npm run build
# 仅涉及本地嵌入 UI 时，使用现有构建入口更新对应产物
npm run build:local

# 仓库根：文档、路径、证据与索引
python3 scripts/repository/check.py --base origin/main
python3 -m unittest discover -s scripts/repository -p 'test_*.py' -v
```

此外按变更运行 Linux amd64/arm64、Darwin arm64、Windows amd64 构建；生产数据库迁移需 PostgreSQL 回放。实际命令、退出码、测试数、skip 和环境故障写入证据，不能把上述命令清单当成已经执行的结果。

### 12.3 合并与发行

- 原则上一 PR 对应一个可验收问题或紧密耦合的工作包。OPT-05 可按合同／迁移／实现／恢复测试拆审，但不得将不可用的中间状态当可交付产品。
- 排除本机原始测评数据、重复实现、过期草稿和未经当前源码重建的 UI 产物。
- 必需检查按当时仓库保护规则读取，不将历史“31 项”硬编码成永久标准。
- 失败的相关检查先定位，不能为合并而禁用检查或改低断言。
- 合并权限以用户当次及持续授权为准；已有适用授权不重复询问，不擅自改分支保护。
- 新修复进入 `main` 不代表已包含在 0.4.1 下载包。新发行使用新身份，独立签名、验签和原生验收，不覆盖旧资产。

## 13. 任务台账模板与完成定义

执行阶段建议以一个 JSON 台账为状态源，Markdown 仅作阅读视图；不得维护两份独立手工完成数。

| 字段 | 要求 |
| --- | --- |
| id / title | 本方案任务编号与具体名称 |
| source_findings | 外部编号及既有 SEC/ENT/UX 任务映射 |
| status | planned / investigating / implementing / validating / blocked / done / not_applicable |
| baseline / candidate | 起始基线与实际验收候选，跨仓库分别记录 |
| scope / dependencies | 文件边界、任务依赖和所需平台 |
| acceptance_cases | 对应测试与真实业务单元 |
| evidence | 命令、结果、摘要和报告位置 |
| residual_limits | 未覆盖场景与对外表述限制 |
| merge / release | PR、主线提交、发行身份；不存在时留空 |

任务标记 done 必须满足其代码、合同、测试和指定实际验收条件。研究任务的 done 仅表示研究交付，不表示产品能力已实现。

**本方案创建时状态**：OPT-00–OPT-15 均为 planned；OPT-01 的问题证据为“已复现”，不等于任务已修复；RES-01–RES-03 为待立项研究。历史已通过的测评不计入本轮新增成绩。
