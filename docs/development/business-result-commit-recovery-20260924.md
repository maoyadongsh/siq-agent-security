# 最终回复提交与资源清理顺序修复

日期：2026-09-24。原结果持久化及 API 故障验收的定向修复；客户端和企业端冻结候选不变。

## 问题与修改

研究业务 Qwen 请求后端原先先调用 finalizer 删除运行资源、结束执行记录，再保存最终回复。如果进程在这两步之间退出，执行可能已显示完成，但既无持久回复，也失去了运行中的副本。新增负向测试在旧行为下实际失败：进入清理函数时，独立数据库会话看到的结果数为 0。

现在，对主任务及子任务均已确认终态的最终回复，先提交不可覆盖的结果和同事务审计，再释放资源及结束执行租约。进程在提交后退出时，重启 API 可按原运行、主体和当前业务授权读回；恢复器仅回收旧执行，不重放任务。未知主任务或子任务不能提前存为可读终态。数据库保存失败不阻断安全清理，也不会伪造持久成功。

本次没有新增数据库表、迁移、HTTP 字段或正文展示权限。结果 `write_quiesced` 继续表示已确认 writer 静默，不代表 Provider、沙箱或全局 owner 已释放；这些事实由原 finalizer 和执行记录独立证明。

## 验证

最终组合验证覆盖结果保存/读取/历史、Qwen 请求 API/finalizer/恢复器、流式/聊天历史及故障证明器，**229 passed / 750 warnings，115.66 秒，无跳过项**。使用单独创建的 PostgreSQL 数据库补跑迁移、并发、审计回滚与重新授权测试，测试库已删除。早期 96 passed / 1 skipped 的结果保留为中间记录，不重复累计。四个变更 Python 文件 Ruff 通过。

真实故障证明使用 E165 家族的新 v3/v4；v1/v2 保留，不覆盖历史故障点。调用真实 HTTP 登录、授权、Hermes/OpenShell/本地 Qwen，仅使用合成业务内容。两轮分别在结果与审计均已 flush、commit 之前，以及 commit 完成、资源清理之前，对证明器自有 API 发送 SIGKILL。

| 故障位置 | 同库重启后结果 | 自动清理 |
| --- | --- | --- |
| v3：事务提交前 | 结果与审计均为 0；准确结果接口返回 404，不伪造已保存回复 | 原执行保留到自然租约到期，122.806 秒后进入 `authority_lost` |
| v4：事务提交后、清理前 | 原结果与审计各 1 条；当前授权下读回原模型标记，匿名 401，撤销 grant 后正文读取 403 | 原执行保留到自然租约到期，122.778 秒后进入 `authority_lost`，已保存结果没有被替换 |

两轮均独立确认沙箱、监督与转发退出，finalizer 已 `released`，子凭据返回 401，且当时诊断父身份仍有效。没有重放或换绑执行，实际模型桥关联 200；临时数据库、API 与身份服务已清理，原服务及预览身份保持一致。这里的 `authority_lost` 是失去原 API owner 后的执行清理状态，不否定提交前已独立确认的模型终态；结果状态不冒充资源已释放。

实际结果以[源码绑定证据](../evidence/flagship-optimization-20260921/business-result-commit-recovery-20260924.json)为准；候选清单（本机私有路径：`var/flagship/result-commit-recovery-20260924/candidate.json`）绑定本报告和证据。明文回复、数据库连接和凭据不进入该证据。

## 部署与限制

修改位于研究仓库的 `apps/api/services/agent_chat_runtime_impl.py`，以及对应测试、隔离证明器和业务结果架构合同。现有 API/预览均未重启，仍加载此前版本；此修复已通过隔离候选验证，尚未部署到在线服务。旧预览源码清单不被重写，下次启动须按新源码生成新的部署清单，不能绕过原摘要检查。

提交前崩溃会回滚未提交的正文及审计，接口不会伪造已保存结果；**本修复不恢复尚未提交、只存在于内存的正文**。只在 finalizer 停止后才能确认的未知 writer 路径仍沿用原后置保存，不能据此关闭全部结果丢失窗口。原未知子任务、其他授权边界、正式报告归属、真实 IAM/审批/事件出口、部署回退、原生 CI 和签名发行仍按原清单推进，`production_eligible=false`。
