日期：2026-10-08。环境：DGX Spark＋智能分析助手＋Hermes 原生 Skill＋OpenShell＋SIQ。

本批补齐前批缺少的正向观察：**旧任务因 API 崩溃而失效、完成资源回收后，同一重启后的 API、同一临时数据库、同一业务会话可以执行新的合法请求；旧执行和旧凭据没有因此恢复。** v850 的 43 项现场检查通过，两次请求对应的回执和签名上下文已独立核验。

## 2. 先关闭失效执行，再验证新任务

| 阶段 | 实际动作 | 核验结果 |
| --- | --- | --- |
| 首个业务请求 | 原生加载 `siq-company-evidence`，读取公司元数据，观察到模型正文 | 原生读取允许，有签名回执 |

旧任务的恢复等待为 **110.850 秒**，从 API 重启就绪后计算，包含原 120 秒租约的剩余窗口与清理时间。首次模型正文等待较长，不能将本批数字作为低延迟承诺。没有修改租约期限、系统时间或数据库终态来加速通过。

崩溃请求再次观察到 `model_access_busy`，确认沙箱删除后记录 `model_access` 恢复，两监管服务均未出现 `supervisor_containment_failed`。这补充了前批模型回收修复的实际运行证据。

**保留模型与工具异常。** 新任务首次 `read_file` 返回工具错误，随后模型重新调用并读取成功，最终完成输出。SSE 中该错误只有布尔标记，尚未完成根因归属；不把它算作防御成功，也不描述为全程无异常。最终成功与首次工具错误分别记录。

## 3. v849 的脚本错误与修正

先行 v849 已完成崩溃恢复和后续新任务读取／输出，但验收脚本错误地要求数据库同时保留两条不可变的 `ActiveRunLease` 行，随后返回 RuntimeError，整例判定失败。

实际合同按 `(profile, session_id)` 唯一定位活动槽位。已结束会话启动新 run 时复用该行；历史证明应来自请求身份、最终化记录和签名回执，不能把活动槽当成追加历史表。SSE 确认 v849 两请求会话相同、run 不同，源码的唯一约束和复用路径与错误断言冲突。临时数据库已清理，此分析没有声称事后再次读取了原数据库。

修正后的 v850 在执行前重新登记驱动摘要，明确验证：

1. 同一活动槽对应新的 run 和原生请求身份。
2. 旧请求在新任务前已经失效，其最终化文件在新任务前后摘要不变。
3. 新请求完成后，旧子凭据仍被拒绝，新请求也完成独立回收。

另用隔离内存 SQLite 调用实际协调函数，核对“结束槽可复用、新 run 不同、旧 run 的释放不能清除新 run”三个不变量。这是组件检查，不能代替真实 PostgreSQL 业务验证。产品代码、授权条件和旧证据没有为适应脚本而改动。

v849 的失败、候选身份、完成到哪一步及清理情况保留在本批结构化证据中；不把该次整例补记为通过。v850 也不与 v849 合称“两次完整通过”。
