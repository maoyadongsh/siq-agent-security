## 二、七条 P1 逐项决议

### 1. 每请求全链验签：接受，保留可利用性限定

证据：`apps/agentshield/internal/server/server.go` 的 `receipts` 调用 `Chain.Read` 后对全部历史 `receipt.Verify`，返回最多 500 条也没有限制前面的读取和验签；`openshell_session_exec.go` 的两处路径有同类模式。

影响：验签随历史数量线性增长；多个请求会放大 CPU 和内存占用。但 `/v1/receipts` 经过 `s.auth`，不能直接描述为未认证互联网远程 DoS。本轮没有完成长链容量或并发压测，不能给出攻击成本、吞吐和延迟数值。

最小修复：先梳理共享调用点、设置并发及资源预算；为热点建立经过验证的快照和可失效索引，避免重复读取/验签。预算不足应返回明确的不完整或失败状态，不能把截断集合当作完整授权历史。纯内部优化可不变更合同；新增分页、完整性或错误字段则先更新合同。

回归要求：历史中段改写、尾部截断、文件替换、并发追加、跨日、重启、密钥/链身份变化均不得复用过期可信状态；增加不同历史规模下的时间、内存和并发基准。

### 2. `Chain.Read` 全量载入：接受，与第 1 条合并设计

证据：`internal/receipt/chain.go:189` 先保留行字节，再解码全部 Receipt；`walkVerified` 已提供流式遍历。另有 `read_limited.go`，原报告遗漏了已有有界读取能力。

最小修复：按消费者语义选择“全量流式验证 + 有界结果”或“可信索引 + 增量读取”，不能简单将每个 `Read` 替换为截断读取。完整历史涉及撤销和会话关联时尤其不能只保留最后若干条。流式化主要解决内存，不会自动消除全链验签 CPU 成本。

合同影响与回归：保持现有完整性语义时无需改外部合同；需要显式表达截断时必须改合同。验证超过页面上限的历史撤销仍有效、大单行被拒、总内存受控、损坏位于返回窗口外时仍能发现。

### 3. pending 截断静默处理：接受缺陷，修正“必然丢未提升记录”的表述

证据：`internal/pending/promote.go:48` 在 `start > len(lines)` 时将游标改为新长度并返回成功；文件不存在也直接返回成功。游标只记录行数，无法识别日志被替换或截断后重新增长。

影响：确有审计来源完整性缺口。严格来说，`start > len(lines)` 本身不能证明消失的都是“尚未提升的记录”，它也可能对应已提升前缀；被删去的未提升尾部、重新写入的短日志和等长替换是需要分别测试的情形。

最小修复：发现截断/身份冲突时保留旧游标、返回明确错误并记录可见告警；设计带日志代次、稳定记录 ID、已确认位置和前缀承诺的游标，补齐提升幂等与崩溃恢复。不以自动重置游标掩盖历史断裂。游标持久化格式变化需要版本与兼容恢复规则。

回归要求：截断至游标前后、整文件删除、等长替换、截断再增长、正常轮转、回执写成后游标更新前崩溃、坏行与重复提升。Merkle 根可以是后续选项，但不能证明从未可靠提交到任何可信来源的事件存在过。

### 4. 隔离创建者可自行释放：部分接受，企业策略需要明确

证据：`routers/threat.py:327` 的释放接口检查独立权限 `quarantine:release` 和状态，未比较 `created_by`；已有 `test_release_quarantine_flow` 明确验证同一用户扫描、隔离、释放成功。

判断：权限点已经分离；双人制尚未实现。两者不能混为一谈。对于宣称双人审批的企业流程，这是缺口；对于个人版本，强制要求第二个用户会使恢复流程无法完成。仅比较扫描者和释放者也不等于完整的“释放申请者不得唯一审批”流程。

建议修复：企业模式使用明确的释放申请/独立审批规则，保留理由、审批身份、修订号和同事务审计；个人模式如允许单人恢复，应清楚标注保障边界。不能在未定义产品策略前加一行判断并宣布完成企业 SoD。此项改变业务及接口合同，需先确定策略和迁移兼容。

回归要求：同人拒绝、独立授权人成功、跨租户隐藏、无权限拒绝、重复/并发释放、过期审批、理由缺失、审计写入失败；释放不得自动恢复此前吊销的运行时权限。个人流程与企业流程分别验收。

### 5. base64 摘要原样持久化：接受风险，修正为“编码原文泄露”

证据：共享规则 `threat-obf-base64-blob` 匹配长度至少 240 的编码块；`_make_match` 将命中内容按黑名单脱敏后保留 40 字符，现有规则没有该编码块的专用屏蔽。合成样本验证得到：命中存在、摘要长度 40、与输入编码块前 40 字符完全相同。

判断：保存的是未脱敏的编码字符串前缀，并非检测器解码后的整段秘密。编码并不提供保密性，因此风险仍成立，且 Go 共享规则/摘要路径需要同步处理。

最小修复：对此类命中持久化固定说明、规则 ID、行号、长度及摘要哈希，不持久化编码载荷片段；根据数据策略决定是否需要带密钥指纹。熵检测仅可补充，不应被当作“所有未知秘密均已去除”的保证。

合同与回归：字段结构可保持，excerpt 语义和规则版本需要说明；共享规则变更必须保持两份一致、更新匹配样例和对等测试。覆盖 base64/url-safe 变体、不同长度、已知与未知密钥、非秘密长字符串；检查 API 响应、Finding、审计、日志和 outbox 都没有合成敏感片段。

### 6. 首次扫描自动写入资产摘要：接受信任边界问题，否定“永久钉死”

证据：`routers/threat.py:126` 将摘要为空的资产直接赋值为本次上传内容的哈希；有权限的资产 owner 可自行扫描。该路径将“待分析输入”提升为资产的摘要事实。

限定：并非任意未授权用户可修改任意资产；也非不可恢复，`routers/inventory.py` 中的新候选摘要能够更新资产并记录观察历史。问题是首次绑定来源及可信等级混淆，不能笼统称为永久投毒。

最小修复：扫描只产生内容哈希与分析结果；权威制品摘要由已验证采集/登记流程确定，或把用户上传明确标为未绑定扫描。缺少可信绑定的结果不能据此声明真实部署制品已通过检查。须检查证据与具体资产/制品版本的关联，不能仅凭同租户某条证据存在就建立可信绑定。

合同与回归：需要明确 bound/unbound、来源和版本语义，必要时升级合同及迁移历史摘要来源。覆盖首次自扫、内容不匹配、绑定证据不属于当前制品、并发首次扫描、可信新版本更新；合法个人自查仍应可用。

### 7. Edge 缺少可操作的设备吊销入口：接受，列为 P1

证据：`security.py:226` 在线检查 `EdgeAgent.revoked_at`；产品路由中未找到设备级吊销赋值，`test_enrollment_flow.py:153` 是直接修改数据库后测试拒绝。威胁扫描和 bindings 路由写的是 RuntimeBinding 吊销，不能算 Edge 设备吊销。

影响：凭据失陷后缺少常规软件可用的处置入口。当前测试只能证明“数据库已经标记吊销时认证拒绝”，不能证明用户能够完成吊销操作。

最小修复：增加设备级管理接口和真实页面按钮，先定位租户内设备，再校验管理权限；理由、时间、状态、审计和 outbox 同事务；重复请求幂等。页面读回结果并显示后续操作，不暴露设备 Secret。明确吊销阻断后续认证，不虚称已经终止所有进行中的进程。

合同与回归：新增管理请求/响应与事件合同；覆盖不同角色、跨租户、重复请求、并发认证、事务失败；真实浏览器点击后再使用旧凭据请求心跳/任务验证被拒，并验证页面刷新仍显示已吊销。

## 三、P2 与架构建议的处理

| 项目 | 决议及最小方案 |
| --- | --- |
| Edge HTTP 重定向 | **提升到 P1。** `edge/agent/client.go:59` 使用默认客户端。初始 URL 强制 HTTPS 并不限制后续跳转；本机 Go 标准库按同域/子域决定敏感头转发，没有按协议降级剥离。受控重定向可能导致认证头经明文传输。最小方案是不自动跟随重定向；若确有业务需要，再定义严格同源 HTTPS 策略。用合成凭据、本地 TLS/HTTP 服务验证降级与跨源均不会发送凭据，并测试正常 HTTPS。 |
| 路径 TOCTOU | **接受边界，执行侧专项。** `receipt/resource_scope.go` 已明确只做决策时校验。Linux 执行侧可采用受信根目录 fd 与 `openat2` 解析约束，实际操作必须消费该 fd；仅返回 inode/device 后再按路径打开依然存在竞态。宿主路径和沙箱内路径要分别处理；保持 Windows/macOS 能力标注。 |
| 同 UID 自批 | **已有明确限制，不能仅靠弹窗宣称解决。** `docs/threat-model.md` 和 challenge 响应已声明 `desktop-same-uid`。单纯跨进程仍可能共享同一身份/秘密；企业强保障需要独立身份、受隔离的授权服务或受保护的人机确认通道。 |
| 黑名单脱敏/熵检测 | **部分接受。** 优先减少持久化原文、按字段和规则生成安全摘要；熵检测有误报和漏报，应有语料评测，不能代替数据最小化。 |
| Connector 文件安全助手抽取 | **延后重构。** 先比较各平台路径/权限语义及负向测试，不按复制数量机械合并。公共包必须符合 Connector 协议边界。 |

### 增量验签不能只增加一个 checkpoint 判断

现有 checkpoint 是已签名的链尖承诺，目录与 receipts 分开，但仍可处于同一 UID/卷信任边界；实现明确不保证整状态目录回滚检测。它不是“之前所有文件从此不可变”的证明。

建议先全量建立可信快照，再在文件/段身份、链/密钥身份、代次和已验证前缀仍有效的条件下增量更新；身份变化、截断和恢复触发重新验证或拒绝。要使历史查询也变快，还需要受验证快照约束的索引。只少做验签、仍每次扫描全部文件，不等于请求总体已变成 O(Δ)。完整性验证命令保留全量流式路径。

### Host Sensor 和风险聚合不抢占当前交付收口

未找到完整 Host Sensor 是真实能力缺口；但受控 Hermes/OpenClaw 适配器、OpenShell 路径和已有运行记录并不因此失效。建议单列 Linux 最小观测项目，明确进程身份/PID 复用、cgroup/容器/沙箱关联、时间来源、丢事件计数及权限。`/proc` 是状态采样，auditd 依赖实际配置；二者存在不等于具备强制阻断和完整事件流。未部署或不支持时页面显示“未接入”，不能显示“已防护”。

风险聚合建议采用版本化、可解释纯函数：输入证据新鲜度、严重度、暴露面、权限和行为，输出风险等级/分数、贡献因素和覆盖状态。区分严重度与检测置信度；缺少采集数据应显示“证据不足”，不能产生低风险安全印象；评分永远不能替代授权或审批。

上述两项可作为后续能力里程碑。当前首先完成用户已经要求的发现、权限、真实按钮和运行结果闭环；不要用缺少综合大屏或主机级 EDR 原型阻塞所有发布，也不要对外承诺尚未实现的范围。
