# 企业部署请求持久恢复（E150）

日期：2026-09-23。承接 E148/E149 / ENT-UX-04。总目标保持 active，外部检查 SEC-F 仍按用户要求后续排期。

## 用户现在可以做什么

确认部署后即保存结果页地址。即使网络响应丢失、提交窗口仍在等待时刷新页面，用户也能从服务端找回同一部署请求和准确部署记录；“刷新记录”只读取，不重新执行。已找回记录时不再持续显示旧的“提交结果未知”提示，执行是否生效仍以下方验证证据为准。

请求还在处理或结果不明时，页面明确说明已保存请求、不要重复部署。遇到已有请求的拒绝可直接进入原部署记录。桌面和手机保留可见的关闭/刷新操作，技术标识折叠。没有把任务创建、配置读回与实际行为验证混为一谈。

## 服务端实现

新增 `deployment-submission-create/v1`、`deployment-submission/v1` 合同，POST `/api/v1/deployment-submissions` 与 GET `/api/v1/change-requests/{id}/deployment-submission`。新 UI 使用此入口；旧部署接口保持兼容，发现已有持久请求时拒绝绕过。

Alembic **0017** 增加 DeploymentSubmission，绑定租户、变更、准确 Deployment ID、请求键与请求/预览摘要。租户+请求键、租户+变更的唯一约束防止并发重复预占。相同请求键/身份/参数返回原状态，不执行；参数冲突或同一变更的新请求键拒绝。

在调用执行器之前，同事务提交 pending Deployment、持久请求和 `deployment.reserve` 审计。审计无法保存就不执行。提交后再次核对授权、绑定、策略和实时计划；变化则记录未执行失败。执行结果与既有部署审计同事务落盘。

进程中断、回执丢失、外部动作完成后审计失败时，已提交请求仍可查询；缺少最终结果的记录保持 pending，不超时回收、不重放。数据库状态未知不能被解释为外部未执行。每份变更只保留一个请求；已知失败后的新操作需重新提出并审批，当前没有自动重试/强行释放入口。

请求查询按租户定位变更再检查 policy:read；返回有界状态与标识，不泄露目标配置、原始异常或凭据。重放 POST 仍检查管理权限。响应明确 no-store。生产 PostgreSQL 的变更行锁覆盖准备流程，新入口在等待锁前先查询已有持久请求，避免不同请求键在正在执行的任务后面无意义排队。
