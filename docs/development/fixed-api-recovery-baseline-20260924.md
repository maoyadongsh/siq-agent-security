# 固定源码 API 冷启动恢复基线（2026-09-24）

已将当前经过验证的 API 固定为独立源码副本，并在原绝对路径、隔离恢复数据库和独立工作流目录下完成首次启动、停止后的冷启动及接口检查。六项检查通过。原主 API 继续运行，尚未进行主端口切换。

## 为什么需要本批

原主 API 从持续变化的工作区启动，不能把今天的源码归档当作该旧进程的历史快照。仅保留旧启动命令不足以证明升级后能恢复。

本批建立的是**当前已测试版本的可冷启动基线**，用于后续部署和恢复；不声称恢复了旧主进程的原始代码。Hermes/请求执行代码还使用原绝对路径定位业务资源，不能随意将代码复制到新目录后启动。

## 实际运行方式

- 固定 1,637 个文件，涵盖 API、OpenShell 脚本、数据库导入模块、Hermes 资产以及已安装的控制包。副本约 24 MB，位于研究仓 `var/ops/main-runtime-delivery-20260924/frozen-source/`；逐文件 SHA-256 见 `frozen-source-manifest-v3.json`。
- 使用现有受控镜像 `sha256:4f8d1afed6d58037c680221ca6dd9fb4737b7ecfa7d4809ca809fdc0c7d9b786`，以 UID/GID 1000、只读根文件系统、全部 capabilities 移除、no-new-privileges 启动。
- 固定源码以只读 bind mount 覆盖容器内原路径；宿主工作区不替换。沿用本机 Python/venv 的只读挂载，因此这是同机恢复基线，**不是独立、可移植的完整依赖镜像**。
- 按原路径提供独立、可写的空工作流状态目录；其他宿主目录只读。未对真实工作流 store 执行恢复或写锁。
- 从主 API 实际连接的 PostgreSQL cluster 创建私有备份，恢复到本批唯一临时数据库。比对完整迁移账本一致后才启动 API；测试中没有新增业务身份或向实际业务库写入。
- 监听 `127.0.0.1:18090`；使用 host network 访问本机恢复库。关闭两类执行恢复器及 primary-market reconcile，保留 `required=true`。没有启动模型推理、OpenShell 沙箱或业务请求。

## 检查结果

1. 独立恢复库的迁移版本与 checksum 均与原库一致。
2. 固定源码首次启动 `/health` 返回成功，恢复门禁保持未开放。
3. OpenAPI 包含报告目录/发布、事件定位结果和执行确认接口。
4. 匿名读取、匿名发布、匿名事件查询均返回 401，响应 `Cache-Control: no-store`。
5. 容器实际停止后重新启动，启动时间改变，相同固定源码再次健康。
6. 原主 API、预览 API 和 Web 的 PID/InvocationID 保持不变。

演练结束后容器与临时数据库已删除；备份、固定源码、私有日志和脱敏结果保留。未把健康检查或匿名拒绝当作已授权业务链路验收。

## 保留的失败与修正

宿主 `unshare` 因 UID 映射权限拒绝，未更改系统配置；因此采用已有受控 Docker 环境。

首轮容器启动因演练 URL 丢失 `+psycopg` 驱动限定失败；第二轮发现已安装控制包的组写归属不能在容器用户表中证明；第三轮发现 workflow 模块导入时需要写锁。分别保留 v1–v3 失败记录，修正仅涉及演练配置、安装包副本及独立工作流目录，未放宽产品源码校验。v4 六项通过，每轮临时数据库与容器均清理。

## 下一步与边界

本批提供了可重新启动的当前版本基线，关闭“只有活进程、没有固定源码恢复验证”的一部分部署风险。主 API 的正式恢复器、执行所需 CLI/宿主资源接入、主端口切换与回退还须验证；不能据此宣布主服务切换完成。

[实际报告权限变更](business-runtime-permission-plan-20260924.md)仍待明确答复，本轮未签发新权限。真实业务身份、生产审批联调、正式发行与原模型/原生平台门禁继续保留。
