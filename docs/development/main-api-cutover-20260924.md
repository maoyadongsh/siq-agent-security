## 切换前置条件与部署选择

启动器逐项复验 1,637 个已测试文件的 SHA-256，再使用原主 API 的受控环境启动。源码仍运行在原工作区，归档与清单用于版本核对；本批不是不可变的完整依赖发行镜像，后续修改源码后不得跳过重新验证直接重启。

保留现有宿主部署方式。之前的固定路径容器演练和 AppArmor 诊断仍保留，但**控制面 API 容器化不是本次发布条件**。本批没有加载新 AppArmor 策略，没有给运行中的业务或智能体容器设置 unconfined，也没有改变 OpenShell 隔离方式。

停止旧主进程前已核对 PID/InvocationID、当前源码、无已建立 HTTP 连接、无未到期 running 租约，并确认备份连接与实际 API 指向同一 PostgreSQL cluster。完整私有备份位于研究仓 `var/ops/main-api-cutover-20260924/before-main-cutover.private.dump`，SHA-256 `27a22be39d081882e2d271ac305e06a111d9da3ac6524f2575fce7351e9a1e67`。备份包含真实业务数据，保持私有，不公开或提交。

没有删除历史 running 行，也没有将租约过期作为远端执行停止的证据。服务自身的恢复器继续按已有合同检查和处理状态。

## 已执行的恢复演练

1. 在停止旧主进程前，使用仅监听 loopback 的 Go 标准库转接程序，于 18091 验证既有 18089 API 的健康、匿名读写拒绝和执行门禁。
2. 正常停止精确识别的旧主 unit，启动新版主 API；读回两类恢复器均 enabled/ready。
3. 核查主 API 新接口、匿名 GET/POST 的 401 与 no-store。
4. 正常停止新版主 API，在**实际主端口 18081** 转接到 18089；读回执行门禁关闭，匿名请求仍被拒绝。
5. 停止转接，重新冷启动新版主 API；InvocationID 已改变、两类恢复器重新就绪。
6. 将原 Web 切换到 18081，复验当前代理目标及匿名接口拒绝，主 API 没有因 Web 切换再次重启。

主切换七项、页面接线三项检查通过。随后再次读取 18081 和页面代理的健康，两类恢复器仍 ready，请求扫描六项计数均为零；18089 保持健康且执行关闭。

**应急转接是降级恢复，不是旧主代码的原样回滚。** 它保留现有 API 的登录、读取与受权业务接口，OpenShell 执行因 required 门禁未就绪而关闭。不能将此演练说成恢复了旧主进程的全部执行能力，也不能自动重放失败中的智能体任务。

## 后续恢复操作

研究仓 `var/ops/main-api-cutover-20260924/` 保存 `launch_main.py`、`cutover.py`、`switch_web.py`、转接源码/二进制、私有日志和脱敏结果。一次性脚本已经执行，不能直接重复运行覆盖本批结果。

需要应急转接时，应先复验 18089 原进程仍健康、执行门禁仍关闭，核对当前主 unit 身份并正常停止，再启动本批摘要绑定的 `fallback-proxy --port 18081`。程序只允许 18081/18091，只转发到固定 `127.0.0.1:18089`，不使用环境代理，不记录请求或凭据。转接失败返回固定 503/no-store。恢复主服务前停止转接，再由启动器重新核对源码并启动主 API；以真实恢复健康决定是否恢复执行。

不覆盖数据库备份、不降级迁移、不重签历史授权。需要恢复旧业务行为时必须有对应版本及兼容证据，本批没有伪造该能力。
