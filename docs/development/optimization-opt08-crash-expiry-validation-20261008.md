## 2. v845：API 死亡后不接管旧执行

测试观察到 `siq-company-evidence` 加载成功、公司元数据读取完成和模型正文输出，确认原请求正在运行且执行租约有效后，才向自有 API 进程发送 SIGKILL。进程退出后保留原执行行，记录其租约期限，再以相同环境、相同临时数据库重启 API。

恢复期间逐次核对原执行的身份绑定及租约：没有替换 run/session/owner，没有人工更新期限，没有恢复模型执行或接管旧任务。原执行租约按代码合同自然到期；恢复器随后将原执行终态写为 `authority_lost`，恢复就绪为 true。

终态还核对了以下事实：

- API 最终化记录为 `released`，原沙箱、监管和转发资源均不存在。
- 原请求的子身份状态为 revoked，旧凭据查询返回 401；父身份仍有效。
- 同一临时数据库完成恢复后才移除，独立 API 监听端口关闭。
- 实际模型桥有对应流启动记录；不把未正常结束的模型流算作成功交付。

**首次清理的异常继续保留。** 监管日志包含 `containment / supervisor_contract` 和 `supervisor_containment_failed`；后续 `ExecStopPost recover` 返回通过，最终资源与 API 恢复检查通过。systemd 保留 `failed / exit-code`、退出码 1，MainPID 与 ControlPID 为 0。现有日志尚未细分最初 containment 的具体子步骤，不能据此断言首次清理已经修复或始终成功。

126.976 秒从重启 API 就绪后的等待开始计算，包含原 120 秒执行租约的剩余窗口、扫描和回收时间，不是“发现故障后立即终止”的 SLA。未安排 API 死亡后的新工具调用，本轮不提供该类调用的拒绝效果结论。

## 3. v846：过期授权不能从队列进入执行

测试先以公开业务 API 签发 60 秒 Grant，再创建一个由测试自身持有、不运行沙箱的合成网关占位。真实业务请求按生产排队流程进入 pending，等待期间仍验证占位归属不变。

授权自然到期后，原 HTTP 请求返回 503、固定 `request_start_unconfirmed`、`retryable=false`，并保持 `Cache-Control: no-store`。数据库检查确认 Grant 的创建／到期时间未改写、没有通过撤销代替到期；原 pending 请求转为 released，没有生成另一条执行或自动重试。

独立复核按请求摘要找到对应 pending 记录，确认阶段为 released、请求目录不存在；前后原生回执链完全一致。原合成占位直到测试清理前都未被该过期请求接管，随后由其所有者释放。

这证明了**授权在排队期间失效时，业务入口不会启动原请求的执行环境**。本轮没有 Hermes、模型或工具执行，不记为一次工具攻击被防御，也没有制造签名 deny 回执。59.404 秒是排队观测时间，授权期限仍为 60 秒，二者计时起点不同。
