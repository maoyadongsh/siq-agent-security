# OPT-15：回执标识与历史审批歧义修复

日期：2026-10-08。基线：`b89d8d12`。状态：本子项完成，OPT-15 开始实施，跨平台最终验收未完成。

## 1. 实际问题与影响

原在线 decision ID 为参数 SHA-256 的前 12 位加日内微秒时间。两个决定若参数相同、时钟值相同，即使链序号、动作或会话不同，也会使用相同 ID；只含日内时间还不能区分不同日期。该问题不是“密码学随机碰撞”的估计，而是在固定时钟的真实引擎测试中确定性复现。

审批原先按 ID 搜索原 hold 和其派生 resolution，可能选中最后一条或复用另一个动作的审批结果。审批 API 仍需管理权限，此结果不证明未经认证可直接批准；问题在于管理者确认的对象可能存在歧义。两项新增反例在修复前均失败：

- `TestDecisionIdentitySurvivesRepeatedClockAndRestart`：不同决定复用了 ID。
- `TestHoldRejectsHistoricalDuplicateIdentity`：面对签名有效但 ID 重复的历史链，审批没有拒绝。

## 2. 修复行为

已先更新[开发规格](../agentshield-dev-spec-v1.md) §3.8，再修改实现。

新在线 decision 使用 `rcp-` 加 128 位密码学随机值，身份不再依赖请求参数、时钟分辨率或进程内计数。随机源不可用时不签发决定，不回退弱标识。没有增加环境变量、HTTP 参数或产品配置来替换随机源。此方案降低碰撞风险，不声称数学上绝不碰撞。

管理审批在流式验签的历史链中检查：原决定唯一存在、传入载荷摘要一致、历史 resolution 唯一且关联原决定和动作、扫描结果匹配当前已知链头。重复原 ID、重复 resolution、关联错配或缺失原决定都不能产生新的审批。歧义返回已有 `ErrHoldConflict`，原 HTTP 映射为 409。

保留 receipt v1/v2/v3 的字符串字段、规范化、签名和链哈希算法，pending 来源幂等标识及派生 ID 规则也保留。唯一的旧格式回执仍能正常审批和幂等读回。历史重复 ID 是语义歧义，不等于原签名无效；历史回执没有改写。

## 3. 验证结果

| 验证 | 结果及范围 |
| --- | --- |
| 固定时间重复请求、引擎重建、相隔一天 | 新决定 ID 不同，分别批准／拒绝，签名链有效 |
| 签名有效的历史重复 ID | 两个候选均拒绝审批，链头不变 |
| 重复 resolution、错误动作／决定关联 | 拒绝复用，链头不变 |
| 唯一旧格式 ID | 审批和同决定幂等读回正常 |
| 实际 Go HTTP handler | 历史重复 ID 返回 409，未追加审批 |
| 定向 race | receipt／server 相关测试通过 |
| Go 全模块加受影响包复测 | 按最终测试身份去重，**1,748 个顶层通过、34 个跳过**；含子测试为 **4,205 通过、36 跳过** |
| 合同 | 17 项 receipt schema 检查通过 |
| 静态检查 | 全模块 vet、改动文件 gofmt 通过 |
| 构建 | Linux amd64/arm64、macOS arm64、Windows amd64 构建通过 |

首轮全量回归有 4 个顶层失败，均为合同样例逐字节比较依赖固定 ID；没有将其隐藏为通过。随机 ID 使每次生成的签名值不同，测试现改为先验证实际链与历史链签名，再以记录位置映射 ID，对比其余字段和决定引用关系。比较器的负向测试确认授权字段变更、错误引用及重复身份不会被归一化掩盖。没有向生产引擎增加固定随机源，也没有重新生成或覆盖历史样例。

随后仅复跑受影响的 receipt、skillcontext 和新测试辅助包：247 个顶层通过、2 个跳过（含子测试 793 通过、2 跳过）。上表总数是首轮结果和这次复测按包／测试名称去重后的最终状态，不是重新运行一遍全量所得；跳过项仍是条件性未运行，不能计入平台验收通过。

## 4. 边界与后续

- 流式验签用于管理审批，未向每次 Decide 增加整链查询；审批仍为线性扫描，未证明大型历史库的性能上限。
- 本次未声称所有只接收 ReceiptID 的历史查询入口均已完成歧义审查；任务追踪等消费者仍需按其合同逐项确认。
- 本次没有更改 token 哈希、依赖锁定或扫描其他生产断言的执行行为；OPT-15 这些子项继续按影响分析处理，不作无依据的机械替换。
- 四目标构建不等于 Windows／macOS 原生安装、宿主执行、升级或恢复，也不等于正式签名发行。
- 本次改变安全二进制。此前真实业务结果仍属于其原冻结候选，最终 OPT-10 必须固定包含此修复的候选并完成受影响核心权限矩阵，不能直接继承旧批次为最终通过。

OPT-15 从 planned 调整为 implementing；主任务完成数保持 **11/16（68.75%）**。其余 OPT-08/10/11/12 和原生平台、签名交付要求保留。
