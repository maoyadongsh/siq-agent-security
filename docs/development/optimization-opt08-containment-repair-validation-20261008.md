# OPT-08/10：模型访问回收故障定位与真实修复验证

日期：2026-10-08。环境：DGX Spark＋智能分析助手＋Hermes 原生 Skill＋OpenShell＋SIQ。

本批定位并修复了前批 API 崩溃恢复中出现的首次清理失败：**已接纳的模型流仍持有 admission 共享锁，首次模型凭据轮换等待超时；删除原沙箱后锁释放，但旧实现没有在同一次清理中再次确认凭据轮换。** 修复后的真实业务试点观察到该冲突再次发生，随后有界重试成功，监管服务正常退出。

这是一次有前后证据的故障修复，不是全部生命周期、性能或跨平台验收完成。

## 1. 诊断依据

前批 v845 已记录首次 `supervisor_containment_failed`、后续恢复通过，但缺少具体子步骤。本批业务提交 `8d2cc2c` 增加固定类别日志，仅输出预定义阶段和错误类别，不输出异常正文、凭据或私有路径。

诊断候选 v847 在真实公司元数据读取、模型输出后，强制终止本轮独立 API，再以原临时数据库重启。原业务租约自然失效，未延长期限或接管旧执行。首次回收明确记录 `candidate_containment_failed stage=model_access`，随后记录 guard 和 containment 失败。

只读观察器读取内核锁表中已知 admission 锁的状态，并核对持有者是否为本轮模型桥。采样显示该失败发生时最近一次观测仍为自有桥持有 READ 锁，约 0.619 秒后观察到锁消失，锁 inode 未变化。观察器没有读取凭据文件；它是周期采样，不能精确确定锁释放的内核时刻。

结合实现中凭据轮换先等待排他锁、超时为固定 `bridge_admission_lock_timeout` 的路径，以及真实锁回归，故障可以定位到在途流与清理顺序的冲突。不能据此将历史所有清理错误都归为同一原因。

## 2. 修复范围与失败边界

业务提交 `8851724` 在宿主清理逻辑中引入严格区分的 `CandidateModelAccessBusy`：只有准确匹配 admission 锁超时才进入此分支，锁损坏或其他凭据异常保持原失败。

清理仍先撤销数据访问并尝试切断模型访问，再删除原沙箱和检查资源清单。只有以下条件同时满足，才对原运行的模型凭据轮换再尝试一次：

1. 首次轮换失败明确来自 admission 锁超时。
2. 原沙箱删除返回确认成功。
3. 独立清单检查返回为空。

重试不创建新执行、不续租、不授予新权限，也不跳过锁。初次等待仍为 10 秒，第二次最多再等待 10 秒；两次等待上限不是整个资源清理的总 SLA。数据撤销失败、删除未确认、清单非空、清单读取异常或第二次轮换失败，均保留失败结果。

首次锁忙日志保留为 `candidate_containment_failed stage=model_access_busy`，确认轮换成功后才记录 `candidate_containment_recovered stage=model_access`。不能仅凭后者抹去其他阶段的失败。

## 3. 相关回归

最终修复共完成 **75 个不同的相关检查**：run guard、supervisor、模型凭据检查 72 项，另有真实文件锁及错误分类检查 3 项。诊断阶段的 61 项与最终集合重叠，不重复累加。新反例在旧清理行为下有 3 项失败；修复后相关检查通过。Ruff 和差异格式检查通过，没有重复执行无修改模块的全量测试。

真实锁回归使用实际文件上的共享 flock 和实际凭据轮换函数：删除确认之前锁仍持有、旧凭据不变；删除回调释放锁后，第二次轮换成功。测试仅压缩夹具等待期限，生产 10 秒期限不变。负向覆盖未确认删除、非空清单、重试失败及其他阶段失败，验证不会误报清理成功。
