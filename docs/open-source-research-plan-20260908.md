日期：2026-09-08。状态：**已进入实施；许可与仓库治理进展见[实施记录](research/operations-20260908.md)，研究发布、外部复现和论文状态分别跟踪。**

任务执行台账：[Markdown](open-source-research-tasks-20260908.md) · [JSON](open-source-research-tasks-20260908.json)。台账登记不等于任务已实施。

## 1. 建议决策

把 SIQ Agent Security 建设为 **Agent Skills 运行时授权与效果核验的可复现研究项目**。

推荐采用：**自有代码 Apache-2.0 + 自有研究材料 CC BY 4.0 + 固定版本研究制品 + 公开复现协议 + 轻量维护者治理**。先让外部研究者能使用、复现、质疑和引用，再扩大实验范围与传播规模。

首轮公开的重点是三个可检查的命题：

1. 模型提出动作后，独立运行时能否依据任务授权和来源约束阻止不允许的执行？
2. 参数值相同时，不同可信来源是否导致不同授权结果？
3. 工具报告成功时，独立效果材料能否识别实际未完成的任务？

DGX 本地分析、StepFun 远程规划和动态 Skills 为这些命题提供可运行的实例。它们不应成为复现基础安全实验的硬件或付费模型门槛。

首轮成功标准建议为：**至少两组外部复现记录，其中一组来自非作者人员；至少一份可长期引用的研究制品；每项对外研究结论都能追溯到运行记录。** 这是未来验收目标，不是当前完成状态。

## 3. 开放范围与许可证设计

### 3.1 开放完整的现有研究链路

| 内容 | 建议开放方式 | 必须保留的边界 |
| --- | --- | --- |
| Go Runtime、Intent、Context、Provenance、Approval、Receipt、EffectEvidence、Completion | 权利确认后的自有代码采用 Apache-2.0 | 检查权利来源；不声称拥有上游代码全部版权 |
| Secure Agent、现有 Skills、适配器、合同、测试与验证脚本 | 与运行时同等开放，可独立复现 | 不以获得专有密钥或 SIQ 其他仓库为前提 |
| 现有 Control API、Edge、Connectors、Web | 继续保留在现仓库，按确认后的许可范围发布 | 首页将研究运行时作为主入口；企业组件作为可选实验表面，不在本轮拆仓或抽走能力 |
| 自有论文草稿、方法说明、原创图表、清洗后的研究数据 | 明确标识的文件采用 CC BY 4.0 | 仅覆盖有权授权的内容；论文最终版本需与投稿/发表协议协调 |
| 测试夹具、脚本和代码示例 | Apache-2.0；有代码的 Markdown 示例明确同样适用 | 不把整个可执行 benchmark 仅标为数据许可 |
| 第三方代码、字体、数据、图片 | 保留各自许可，并列入文件级清单 | 不自动重新许可为 Apache-2.0 或 CC BY 4.0 |
| 原始含身份或密钥的运行状态、用户数据、未披露漏洞材料 | 不进入公开研究制品 | 使用已有白名单导出公共证据；限制访问直至完成处理 |
| StepFun 凭据、模型权重、DGX 系统镜像 | 提供配置说明和外部来源引用 | 不纳入仓库许可，不承诺代为取得模型/API/镜像分发权 |

### 3.2 为什么推荐 Apache-2.0

对于研究传播，宽松的使用和集成条件更便于其他实验室复现、修改和建立对照。Apache-2.0 同时规定版权授权、相关专利授权和再分发义务，不要求把下游修改普遍回馈给上游；商标使用也不自动随代码授权。项目应接受可能出现商业使用和竞争性分发这一取舍。[Apache-2.0 正文](https://www.apache.org/licenses/LICENSE-2.0)

| 方案 | 适合的优先目标 | 本项目建议 |
| --- | --- | --- |
| Apache-2.0 | 容易使用、复现、集成；明确相关专利条款 | 推荐为自有代码的统一基础许可，与已有 Skill 声明方向一致 |
| AGPL-3.0 | 重视特定网络交互场景下的修改源码可获得性 | 当前不推荐；研究采用成本和合作方许可评估会更复杂 |
| 禁止商业使用的自定义许可 | 限制使用方式 | 不作为本方案的“开源软件”许可；与 OSI 对使用领域不歧视的要求不同 |

AGPL §13 针对修改后的程序通过网络与用户交互时提出相应源码获取要求，不能概括成“使用 AGPL 就必须公开公司全部代码”。[AGPL 正文](https://www.gnu.org/licenses/agpl-3.0.html) 开源许可不能禁止商业领域使用。[OSI 定义](https://opensource.org/osd)

CC BY 4.0 用于本项目有权授权且逐项标识的研究材料，要求适当署名、许可链接和变更说明；它允许分享与改编，包括商业用途。代码不因此转为 CC 许可。[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

### 3.3 许可落地方法

1. 确认授权主体和贡献来源：作者/雇主/合作方权利、引入补丁与复制片段。Git commit 的作者名、AI 工具署名或提交数量都不能单独证明版权归属。
2. 根 `LICENSE` 放未经改写的 Apache-2.0 标准文本；在 README 与文件级映射中说明第三方及研究材料例外。
3. `THIRD_PARTY_NOTICES.md` 记录来源 URL、版本/commit、文件路径、原许可、修改情况及所需归属文本。保留 OpenClaw 的 MIT 文本；核查 Mermaid bundle 与字体的实际分发内容，不仅检查直接依赖声明。
4. 在 `LICENSES/` 放适用的研究材料及第三方许可文本，增加明确的文件许可映射。原有 `docs/` 不自动整目录改为 CC BY，因为其中混有代码示例、外部材料和历史证据。
5. `NOTICE` 仅在确有归属通知内容时添加，并继承所需上游通知；不将它当作所有 Apache 项目无条件必需的空文件。
6. 新增文件按确定范围使用 SPDX 标识；对历史文件逐步核对。`apps/web/package.json` 的 `private: true` 是包发布控制，不是该代码的许可证。
7. 对已冻结的 V5 RC 保留原始内容和哈希。新许可、新归属文件应随新的研究源码提交与新候选制品一起发布；不默认将新声明追溯覆盖所有历史制品。

本提案不替权利人选择授权主体，也不直接赋予或变更现有代码许可。完成清单是正式许可发布的前置条件。

## 4. 研究定位与结论边界

推荐公开名称继续使用 **SIQ Agent Security**，英文定位建议为：

> A reproducible research system for runtime authorization and effect verification of Agent Skills.

中文：**面向 Agent Skills 的运行时授权与效果核验研究系统。**

### 4.1 候选研究问题

| 编号 | 可研究的问题 | 现有材料 | 尚需补充才能支持更强结论 |
| --- | --- | --- | --- |
| RQ1 | 独立授权是否能阻止已提出的不允许动作，并保留正常任务效用？ | 23 项受控 Agent 测试与运行时基准 | 公平对照、多任务族、不同环境与预先定义的统计协议 |
| RQ2 | Value + Provenance 相比仅匹配参数值，在哪些场景改变结果？ | same-value、伪造来源、跨任务/会话来源等记录 | 受控消融和独立未见测试集 |
| RQ3 | 工具成功与真实效果不一致时，Completion 是否反映证据状态？ | fake-success、conflicting、缺失效果记录 | 更丰富但明确限定范围的 observer 故障与效果任务 |
| RQ4 | 本地敏感分析与远程规划的分工，能否保持预定数据边界？ | DGX canary、HTTP 摘要、本地连接失败零远程调用 | 不同输入分类、策略和基础设施的测试；分类错误单独评价 |
| RQ5 | 1/2/3 Skill 任务组合在约束下保留多少效用、增加多少成本？ | 动态 Skills、研究/报告/交付和模型调用记录 | 同任务、同模型/预算的对照，阶段时延与错误归因 |

这些是候选研究问题，不是已被同行评审接受的原创贡献。论文准备阶段应先完成相关工作检索和差异分析，再确定贡献措辞、题目及投稿方向。

### 4.2 首发允许引用的数字

只复用 V5 已冻结的 canonical 结果：23/23 控制预期、正常完成 5/5、不安全目标工具执行 0/13、来源违规阻断 8/8；StepFun 和 Ornith 最新保留 cohort 各 5/5。明确写出：**small controlled sample；早期 4/5 失败保留**。见 [V5 报告](hackathon/final-release-report.md)。

不将以下事项混为一谈：

- 确定性 FixtureProvider 主动提出攻击，测量的是运行时执行边界；它不是实模型受到提示注入影响的概率。
- D3 工具入口、独立效果观测和 Completion 是不同层次；缺失证据不是“证明没有恶意效果”。
- 文件与受控 HTTP receiver 的效果证明，不等于通用 SaaS 业务结果证明。
- 验签证明被检查材料的内部完整性/关联性；随报告携带的公钥本身不能独立认证发布者身份。
- 普通主机功能复现、真实 DGX 推理验证、其他系统交叉编译是不同范围。
- 新机器上的维护者复测不称为外部独立复现；平台的正式 artifact badge 也不能由项目自行授予。

## 5. 面向三类读者的复现路径

| 入口 | 面向人群 | 硬件与服务 | 成功标准 |
| --- | --- | --- | --- |
| A：了解与演示 | 初次访问者、学生 | 普通受支持 Linux 主机；显式 test 模式；无需付费模型密钥 | 完成 normal、MCP、same-value、fake-success，能解释不同结果 |
| B：确定性研究复现 | 安全研究者、复现者 | 现有 Go/Python/Node 依赖；本地 fixtures 与 receiver；无需 DGX | 固定 corpus、预期和证据验证通过，生成独立运行目录与结果 |
| C：真实模型/硬件研究 | 有模型账号或 DGX 的研究组 | 自配 provider；DGX 路径需真实硬件与本地模型 | 记录模型配置、数据分类、运行成本和错误；不要求与历史模型输出逐字一致 |

无模型密钥不应阻塞 A/B。这里的“无需付费模型”不等于首次安装依赖完全离线；系统和依赖要求需在复现指南中列清。模型服务不可用时，应标记该轨道未运行，不用 fixture 替换后仍标为真实模型结果。

现有可复用入口：

```bash
# 先按仓库说明安装锁定依赖；显式采用 fixture 模型的浏览器演示
./scripts/hackathon/start.sh --mode test
./scripts/hackathon/healthcheck.sh
```

确定性基准复用 [Agent benchmark](../benchmarks/hackathon/README.md) 与 [runtime-security benchmark](../benchmarks/runtime-security/README.md) 的现有命令。每次采用新的 state/output 路径。未来 `REPRODUCIBILITY.md` 应提供复制即用的步骤与失败诊断，而非再实现一个实验执行引擎。

GPU 调用不得进入普通外部 PR 的必需 CI。维护者可在获准的受控设备上执行 C 轨道并发布证据；任何外部贡献代码都不能自动获得模型凭据、发布密钥或共享 DGX 执行权限。

### 6.1 每个研究制品的最低内容

| 材料 | 内容 |
| --- | --- |
| Identity manifest | 运行源码 SHA、文档 SHA、corpus/verifier digest、构建工具与依赖版本、平台、制品摘要 |
| Protocol | 任务集合、分类/攻击条件、预期、排除标准、重试/超时政策、重复次数、分析方法 |
| Results | 原始已清洗报告、失败尝试、验证结果、重新生成表格的方法；不打包私钥/token/整个状态目录 |
| Dataset card | 来源、许可范围、合成/真实标记、任务分布、已知重复/污染、使用限制和适用人群 |
| Claims table | 每条结论对应实验、分母、证据路径、适用范围、未被证明的部分 |
| Environment | 普通 Linux 复现与 DGX 实测分别记录；模型名称、版本/日期、生成参数和远程外部边界 |
| License/attribution | 实际分发文件对应的许可与归属说明，第三方例外明确 |
| Citation | 作者确认后的姓名、角色、ORCID（如有）、软件版本、发布日期、仓库与有效标识符 |

复现分三种：确定性判定复现、统计/功能结果复现、逐字节构建复现。当前可优先承诺前两类的明确适用范围；包含时间戳的包哈希不能被用来要求每个复现者生成完全相同的压缩包。

### 6.2 引用与长期保存

- 先提供真实的软件引用；论文尚未发表时不虚构论文标题、作者排序、接收状态或 DOI。代码贡献、数据贡献与论文作者资格分别按实际贡献确认。
- `CITATION.cff` 合并进默认分支后，GitHub 才会据此提供引用入口；它不等于已经注册 DOI。[GitHub CITATION.cff](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-citation-files)
- 权限和许可准备好后，将选定版本归档到 Zenodo。完成集成后，GitHub Release 可以触发归档；必须检查实际处理结果、归档文件和 DOI，不能只看按钮已开启。[Zenodo 发布归档](https://help.zenodo.org/docs/github/archive-software/github-upload/)
- 方法论文或实验报告应引用实际评估版本的标识符，同时提供项目入口。源码存档、研究数据、视频及 Release 附件分别检查是否确实归档，不能默认源码快照包含所有二进制附件。
- 后续许可证/文档变更生成新的研究版本；旧 V5 文件和失败证据不覆盖。对历史敏感材料需要处置时发布经过核查的勘误/替代清单，而非悄悄改写数据。
- 自建复现记录可以说明“外部人员已复现哪些结果”；没有获颁的正式评审标识不展示。可参照 [ACM Artifact Review 政策](https://prod-www.acm.bloomreach.cloud/publications/policies/artifact-review-and-badging-current)设计材料，但当前不宣称通过该评审。

## 7. 后续论文实验协议

以下为比赛冻结之后的新研究周期设计，本轮不扩充 benchmark 或变更运行时。

1. **先固定协议再运行。** 锁定任务族、模型版本、条件、生成参数、预算和排除标准；将试验性调参集与最终评价集分开。新增未知案例单独报告，不追溯改变 V5 的分母。
2. **让对照可解释。** 同任务和工具环境比较模型/提示约束、运行时授权、额外来源约束、额外效果核验的差异。关闭任何保护的消融只允许在隔离的合成 fixtures 中作为实验条件运行，不做用户安装模式或生产默认项。
3. **分开攻击提出与执行成功。** 报告 proposal、attempt、materialization、effect、completion 五种结果及实际观测缺口。模型主动拒绝攻击和运行时拒绝动作要分别记账。
4. **所有尝试保留。** 超时、模型格式错误、服务故障、准备失败均有记录；是否计入某指标按预定总体决定。重试同时保留原尝试，不以最终成功覆盖第一次失败。
5. **多次运行不等于独立任务。** 同一任务的多 seed/重复属于相关样本；统计方法应考虑任务分组。先做 pilot 估计变异，再确定样本规模与置信区间，不把历史 5/5 宣称为可靠性保证。
6. **核验分类和来源的信任假设。** 增加错误分类、错绑上下文等研究条件时，应说明它们属于可信输入假设被破坏，还是运行时实现缺陷，不能统一计为模型问题。
7. **成本按阶段分解。** 分别统计模型推理、授权、回执/持久化、工具与效果核验。统一硬件和任务范围后再做性能比较；记录实测调用量与当时账单口径，不编造成本节省。
8. **复现不绑定同一家模型。** 保留无需模型的控制轨道；其他 provider 的结果按新 cohort 报告。不能把更换模型、提示或 receiver 的结果与原 cohort 直接合并。
9. **相关工作在论文前补齐。** 建立威胁模型、策略输入、执行覆盖、效果验证、实验公开性五列对照；只有可公平运行的系统进入量化横向比较。

## 8. 贡献、维护与安全披露

### 8.1 研究社区的贡献入口

建议 GitHub Issues 使用六类模板：复现报告、基准新案例、数据/指标纠错、适配器兼容性、文档问题、研究提案。安全漏洞使用私密入口，不要求先提交公开 PoC。

第一批 `good first issue` 建议：

- 在普通 Linux 主机复现现有 23 项控制并提交环境与报告摘要。
- 独立验证 same-value 案例的参数来源、SIQ 决策与 receiver 结果。
- 完善 fixture 模式安装诊断，修复无需 DGX 的复现文档。
- 核对一组论文图表/表格与 canonical JSON 的分母。
- 为已复现的边界行为补一条明确的负向测试。

不以扩大框架适配数量、引入新沙箱或增加大量无法独立核验的攻击文本作为首批社区任务。

### 8.2 轻量治理

- 初期由现仓库维护者负责合并与发行；新增研究实验通过 Issue → 协议评审 → 实现/运行 → 证据审阅 → 归档。
- 建议采用 DCO 1.1 和 `Signed-off-by`，以贡献者声明其有权提交为基础。DCO 是来源声明，不是版权转让，不保证所有历史材料自动拥有合法权利。[DCO 原文](https://developercertificate.org/)
- 初期不为研究传播增加强制版权转让式 CLA。未来若改变商业/授权模式，应单独讨论新增贡献条款；不能靠新条款追溯收回已经授出的许可。
- 运行时安全语义、签名/来源合同、统计分母和发布流程的变更，争取至少一名非作者复审。第二维护者尚未到位时明确标注自审，并以 CI/证据补充；不伪造独立审阅。
- README 保留贡献和致谢入口；论文作者资格依据实际研究贡献确认。建议引用项目属于学术规范，不在 Apache 许可之外偷偷追加“必须引用论文”的代码使用条件。

### 8.3 漏洞报告与历史处置

1. 建立 `SECURITY.md`：报告入口、维护版本、必要复现材料、数据清洗要求、沟通与修复流程。
2. 建议开启 GitHub private vulnerability reporting 并验证可用；启用前不发布一个无法接收报告的指引。公开仓库管理员可开启该入口。[GitHub 私密漏洞报告](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository)
3. 建议内部目标为三个工作日确认收到、十个工作日给出初步处理状态；这是待维护者接受的工作目标，不是已承诺的服务 SLA。披露时点根据影响、修复和报告者协作决定，不机械保证固定期限内全部修复。
4. 在推广前核查 CI 注释提及的历史 signing-key blob，以及公开提交历史、tags、旧 release 和归档。只输出路径、摘要和分类，不在报告中重现敏感值。
5. 如果涉及真实仍有效凭据，先吊销/轮换与评估影响；删除文件或重写 Git 历史不等于已撤销凭据。若为测试用材料，明确测试范围及不可用于正式发布的事实。
6. 是否重写已公开历史、如何协调 forks/镜像/归档，由独立处置计划决定；本设计阶段不执行 force push、历史重写或删除公开研究材料。

## 9. 发布与供应链

复用已有 `ci`、`runtime-security`、gitleaks 校准、锁定依赖、四平台交叉构建、package verifier 和 V5 元数据，不建立第二条无关的发布链。

在新研究版本增加这些发布条件：

- 代码和材料许可、第三方归属及历史风险复核完成。
- 新版本精确 SHA 的远端 CI 通过；当前最新 main 不能只用旧 `d127711` 的 CI 结果代替。
- 从干净源码重建；包中提供 source-info、SBOM、Skill inventory、checksums、研究协议和证据入口。
- 当前 RC SBOM 仅覆盖限定的本地产品依赖范围；若发行 Control API/Edge/Connectors 的完整研究部署，补齐实际分发范围的清单，不称旧 SBOM 已覆盖整个仓库。
- 正式 publisher authentication 与哈希完整性分别标识。真实密钥未就绪时允许清楚标为 unsigned 的研究候选；不得以测试密钥充当正式发布者。
- 可考虑 GitHub Actions artifact attestations 记录源码与构建流程来源，但必须验证具体仓库/工作流身份；该证明不会自动替代项目现有 publisher key 的信任规则，也不是实验正确性认证。[GitHub 制品证明](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)
- 仓库主分支规则要求 PR、实际 job contexts、conversation resolution 和禁止 force push；CODEOWNERS 的强制效果以设置读回为准。
- 对 fork PR 保持最小权限，不向不受信代码暴露 provider 凭据或签名密钥。平台 secret scanning、push protection 和依赖更新配置逐项开启、核验；不因某设置启用就声称没有供应链风险。

新许可和研究导航会产生新的源码身份，发行前选择未被占用且符合现有规则的 prerelease tag，重新查询远端，不能覆盖 rc.1 或已有 tag。V5 的原始 RC、视频和 submission manifest 作为历史研究基线继续保存。

## 10. 传播顺序与社区指标

### 10.1 首屏与首发材料

README 首屏建议只出现：研究问题、一张最终架构图、fixture 快速开始、三个可复现实验、结果边界、引用入口、研究指南。现有企业组件说明保留在后续导航，不抢占研究入口。

首发交付五件套：

| 材料 | 面向读者 | 验收标准 |
| --- | --- | --- |
| 研究导读 | 第一次访问者 | 解释问题、机制、实验与限制，英文正文配中文导读 |
| 方法报告/technical report | 安全与系统研究者 | 每条结果能定位代码、协议、分母和失败样本；明确尚未同行评审 |
| 可引用研究制品 | 复现者/论文作者 | 版本、来源、许可、归档链接真实有效 |
| 2–3 分钟演示 | 学生、活动与讨论参与者 | 优先复用已有视频并保留其源 SHA，不为轻微文案重复录制 |
| 外部复现指南与模板 | 合作者 | 能提交硬件/源码/命令/报告摘要/偏差说明，无需共享私密状态 |

先邀请少量外部研究者复现，再公开技术文章和活动演示。以 Artifact/系统演示/安全与系统 workshop 的材料要求准备技术报告；具体会场、截止时间、匿名投稿和预印本政策，应在选定 venue 后重新核对，不在本方案中虚构当前征稿信息。

不自动向他人发邀请、发布帖子或提交论文。研究合作沟通、作者名单、归档账号授权和外部发布由项目负责人决定。

### 10.2 指标优先级

| 优先级 | 指标 | 计算口径 |
| --- | --- | --- |
| 第一 | 外部复现成功率与失败原因 | 成功外部复现 / 所有已提交的外部复现尝试；维护者自测另列 |
| 第一 | 结论可追溯率 | 已绑定证据与统计脚本的对外结论 / 全部对外实证结论 |
| 第一 | 首次复现阻塞数 | 按依赖、配置、硬件、模型、证据验证分类，记录修复周期 |
| 第二 | 有效外部贡献 | 合并的新案例、验证器改进、纠错与复现文档；不只计算 PR 数 |
| 第二 | 研究使用与引用 | 可核实的论文/报告引用、复现实验与课程使用；区分软件引用和论文引用 |
| 辅助 | Stars、访问、下载 | 作为传播触达指标，不等同于安全有效性或研究认可 |

不为获得更多模型成功率或更好宣传数字隐藏失败，不把复现者身份、环境或联系方式作为默认公开遥测采集对象。
