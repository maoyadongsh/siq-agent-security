## 外部依赖与交付门槛

1. **宿主能力：** M02、M04、M05 及 WorkBuddy 的 M03 若缺官方可用检查点/来源/装前钩子，需上游接口或可信替代设计；在此之前保留拒绝或 `unknown`，不以“产品代码已写”宣布宿主通过。
2. **Apple 正式发行信任：** 本机只读检查未发现可用 `Developer ID Application` 身份，亦未取得公证凭据。正式签名、`notarytool` 公证、staple、Gatekeeper/隔离属性和真实安装升级必须由有权持有人提供受控凭据/发行流程后另行完成。开发二进制或 ad-hoc 签名不算此门槛；不得关闭 SIP/Gatekeeper。
3. **独立审阅与合并：** PR #69 当前请求维护者审阅。审阅者应检查候选/证据身份、失败和未测项；代码子批可在审阅及必需 CI 后合并，但这不关闭 M01–M11 或 N09。正式发布、仓库治理变更与签名标签另需明确授权。

## 建议执行顺序与收口规则

先做 **M01** 锁定共同候选并复测现有三宿主能力，同时把 **M02–M05** 按宿主接口证据拆成可审阅修复或真实 `blocked`；然后并行推进不依赖宿主新接口的 **M06–M10**，最后由 **M11** 汇成 A01–A12 与完整矩阵。每次运行内容变化重新固定 SHA/二进制摘要并重测受影响项目；只增加文档/证据时保留原实现候选身份，不回填旧结果。

每批遵守[共享验收规则](personal-platform-collaboration-acceptance-20260913-202355.md)与[材料规格](personal-platform-validation-spec-v1.md)：隔离 Go/state/HOME/profile，禁止 sudo、全局 PATH 与系统安全策略更改；不上传私钥、token、配对码、账号或原始提示。`platform_acceptance.py verify` 的普通退出 0 只证明结构，`--require-native` 退出 3 表示仍缺原生覆盖；只有同一候选的必需原生链路、A01–A12、失败恢复和独立审阅均满足，才可申请 Mac-P00–P05 / N09 整体验收。
