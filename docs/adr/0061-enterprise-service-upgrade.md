# ADR-061：企业用户服务升级与恢复

日期：2026-10-08。状态：实施中（OPT-11）。

## 问题

既有 `install-user-service` 只创建配置或接受相同字节重试，正确拒绝覆盖不同单元。
`setup-enterprise` 是可恢复的分阶段安装，不是对旧设备的升级事务：确认新采集计划后，
服务配置仍可能因与旧单元不同而失败。因此不得把重跑 setup 或手动切换目录称为升级验收。

## 决策与实施顺序

1. 先提供只读 `review-enterprise-upgrade`：读取当前私密设备状态，以已确认旧计划复验旧
   签名暂存，以新的当前计划复验新签名暂存；固定发布公钥，不接受调用方的验签结论。
   旧计划的安装窗口允许已过期（不是重新安装旧包），新计划须在窗口内。
2. 明确绑定设备、租户、环境、控制面 origin、本机架构、旧/新完整采集计划、两份暂存路径、
   当前状态文件原始字节摘要、准确状态/服务路径及旧/新预期 unit 摘要。拒绝跨租户、目标、
   架构、service_mode 变化和自定义旧 unit。状态与 unit 在核验后再次读回，变化即拒绝。
3. 确认摘要为完整 intent 的 Python 兼容规范化 ASCII JSON SHA-256。正文显示新旧范围，
   但不显示设备 secret、签名 seed、公私钥配置或状态正文。review 不创建锁/目录，不探测
   connector，不访问控制面或调用服务管理器；签名核验不等于服务已停或更新已完成。
4. 后续切换命令须重新构造同一 intent 并核对显式确认摘要，在现有任务排他锁下确认服务
   已停止。不得自动停止用户服务或把 status=active 当作可更新。改变凭据/周期确认状态的
   其他未完成事务须先恢复，不能覆盖或清除其日志。
5. 切换前持久记录升级意图和恢复所需的旧/新计划、旧/新 unit、身份基线摘要；不额外复制
   设备 secret 或签名私钥到公开材料。任何状态/unit 的混合中间态都须保留恢复标记，
   正常任务入口拒绝运行，直到明确完成或恢复旧安装。不得仅靠回滚异常内存补偿。
6. 后续恢复命令只接受 journal 绑定的已验签旧/新制品及预期状态，遇第三种字节/身份漂移
   拒绝；旧历史保留，不清除执行台账，不重新注册设备，不改变周期计划确认的授权范围。
   完成配置切换与服务启动分列；启动失败不伪称已恢复业务。

## 本批范围与边界

本批实现第 1–3 项只读核验及版本化 intent，后续事务/恢复不得重新发明确认格式。
第 4–6 项仍为后续实现/验收要求；没有入口可根据本批 preview 自动写入或升级。
只读核验中的同 UID/root 管理员仍是信任边界，不是远程证明。版本切换必须显式显示两份
发行身份；本期没有发布者在线撤回列表，不宣称通用防降级。Windows/macOS 明确 unsupported。

验收要求：正确旧/新来源及过期旧安装窗口可核验；新窗口过期、跨上下文、签名失败、
状态/计划/unit 漂移、路径别名和取消均拒绝；成功/失败/输出故障都没有安装副作用。
完整升级另需故障注入、实际签名包、服务管理器、任务执行及恢复验收。
