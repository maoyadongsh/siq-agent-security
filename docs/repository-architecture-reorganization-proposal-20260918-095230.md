## 1. 结论与本轮边界

推荐保留现有单仓多应用结构，采用“入口先统一、研究资产逐步归位、平台交付单独导航、测评结果独立呈现、运行代码稳定不动”的分阶段调整。

本方案回答四个核心问题：

1. **文献研究应成为根级研究资产。** 根目录建设 `research/`，研究问题、文献、方法、实验设计和结论可直接发现；不再把全部研究主线埋在 `docs/`。
2. **操作系统应有各自的交付入口。** 根目录建设 `platforms/linux/`、`platforms/macos/`、`platforms/windows/`，组织安装、生命周期、诊断、验证及限制。OS 专属源码仍位于其所属模块，不复制三套产品。
3. **测试结果应有独立入口。** 根目录建设 `evaluations/`，区分工程验证、研究测评、外部复现与已知缺口。单元测试留在代码旁，基准执行器保留于现有 `benchmarks/`。
4. **第三方测评应明确可见且可核验。** 先采用 `evaluations/external/`，在根 README 显式链接；不同时新增含义重叠的 `third-party/`、`results/`、`reports/`。真正独立的机构测评与合作开发者自测分开记账。

v1.2 修订阶段未搬迁目录或重跑研究实验。当前实施增加独立目录导航及发行复验工具，原生烟测仅使用私有临时状态，不改变用户服务。用户随后明确要求“先确认开发提交并合入 main，形成一版后再优化”，因此另行完成本地成果核查、历史分支合并关系收口及基线提交，详见[核查报告](local-development-integration-audit-20260919.md)。此后主线已推送，0.3.0 已签发为普通 GitHub Release 并设为 Latest；“先整合、提交一版，再优化”的前置已满足。旧工作树未清理。用户随后已授权将本方案作为持续实施目标；本轮按 RA 台账逐批验证和合入，不把发行完成记作目录重组完成。

默认决策：产品与可复现研究并重，不把当前仓库直接改造成纯论文代码仓；研究方法和脱敏公开材料优先开放，私人状态、客户材料、凭据与未审查原始输出独立受控保存。

相较 v1.1，本轮优先优化六点：

- 基线从集成前快照更新到 `710e12a`；已核查的 49 个本地分支 HEAD 均在 main 历史中，旧草稿不重新整体导入。
- 正式发行已经存在：保护 0.3.0 的标签、八个附件及校验记录，源码整理不覆盖已发布内容，也不重新要求完成已有签发。
- 中英文 README 已更新产品定位、安装入口和证据；剩余入口债务转向 `AGENTSHIELD.md`、Skill 使用说明和旧 current，不再把“重写首页”列为首要任务。
- 首批先统一导航、建立冻结范围和路径检查；研究正文、论文全文与脚本搬迁均为可选子批，不以把目录树全部建齐作为完成标准。
- 发行构建已有 `scripts/release/package.py` 和八项 CI 单测；补齐可复用的最终包验证与发布回读工具，避免下次依赖本机临时脚本。已有 14/14 记录不是这套工具已纳入仓库的证明。
- 将发布状态、制品验证、源码 CI、平台实机验收分别展示；正式版并不使 Linux amd64、macOS、Windows 或全部宿主自动达到完整验收。

本轮方案验证：33 个本地文档链接可解析；`python3 scripts/check_research_task_ledger.py`、`python3 scripts/research/check_metadata.py`、`python3 scripts/check_capability_honesty.py` 均通过；研究主张清单的 10 条证据摘要保持一致。此次结论仅覆盖方案与现有静态守卫，不替代未来迁移或原生安装验收。

```text
文献与研究问题
    ↓
威胁模型、方法与可检验假设
    ↓
产品实现 / 合同 / 平台接入
    ↓
基准与集成验证工具
    ↓
测评记录、证据校验与人工复核
    ↓
研究结论、能力说明与新的问题
```

这个链路是索引与工程反馈关系，不应被实现成“研究报告自动授予权限”或“测评通过自动宣布 supported”。

### 3.2 三个根级入口，一套职责划分

- `research/`：为什么研究、依据是什么、提出什么方法、结论能支持什么。
- `platforms/`：各 OS/架构/运行形态怎样部署、使用、排障和验证。
- `evaluations/`：谁在何时以什么候选测了什么，结果与局限是什么。

`docs/` 继续承担产品文档、架构规范、开发协作和运维手册；不是所有 Markdown 的兜底目录。

### 3.3 保持现有信任边界

不把本机 Grant 与企业权限混成同一个新模块；不因去重让适配器拥有签名私钥或自主判定权限；不改变 fail-closed、来源绑定、审批唯一消费、未知结果保持不确定等不变量。

目录调整不得同时更改授权算法、状态协议、签名规范、运行端口、默认采集开关、托管源 SSRF 规则或产品支持范围。

### 3.4 一份正文、多处索引

每类规范指定唯一维护位置。其他入口链接它，必要时提供简短摘要；不手工同步多份完整副本。

旧证据被多个入口引用是允许的，但必须明确其候选和范围；重复引用不增加独立实测次数。

### 3.5 开发源码、验签样本和发行包分开管理

沿用 #90 已落地的边界：`skills/siq-agent-security/` 是可变开发源码；`apps/agentshield/testdata/releases/siq-agent-security-v0.2.0/` 是保留旧公钥、清单与字节的历史验签样本；正式包来自单独暂存并重新签名的候选。后续目录整理不得将历史清单复制回开发树、让 unsigned bootstrap 成功，或把 fixture 当成推荐安装包。

同样区分研究源码预发布的 Sigstore 签名、产品发行清单签名与运行时本地记录签名：它们绑定不同对象和身份，不能合并成一个“已签名”状态。源码 PR 的验证不需要正式发行私钥；发行步骤继续遵循现有流程和授权边界。

新增的正式发行记录是长期路径契约：`docs/evidence/releases/<version>/` 保存公开摘要、验证及发布回执，实际 ZIP/程序留在 GitHub Release。0.3.0 已发布，禁止以“整理”覆盖同版本附件、移动 tag 或重新签名原包；新源码需要发布时使用新版本和独立候选。`SOURCE-INFO.json` 中 `published: false` 是打包时状态，是否公开、是否 Latest 由独立 `publication.json` 的查询时点记录，不回写包内元数据。

现有 `.github/workflows/release-signing.yml` 处理的是研究源码资产的 Sigstore 签名，不是个人客户端发行者 Ed25519 流程；目录方案不得把两条信任链合并，也不得因已有工作流就声称客户端自动发布已经实现。

## 6. 平台交付架构

### 6.1 一个核心，两个正交维度

操作系统负责路径、ACL/权限、进程、服务注册、通知和安装包差异；宿主负责配置、钩子、版本探测、SEC 归属、工具映射和受控启动。用矩阵组合它们，不建设八个互相复制的产品目录。

| OS | 当前产品范围 | 验证要求 |
| --- | --- | --- |
| Linux | OpenClaw、Hermes | amd64/arm64 分别记录；第六/第八代候选分开；原版与受控补丁宿主分开 |
| macOS | OpenClaw、Hermes、WorkBuddy | Luke 的阶段成果与最终同候选验收分开；GUI 与 CLI 分开 |
| Windows | OpenClaw、Hermes、WorkBuddy | 已合入阶段实现；现有 OpenClaw WSL Agent、Hermes 原生 CLI、WorkBuddy 原生最小旅程分别登记；完整复测仍待 |

Linux/WorkBuddy 不作为当前交付任务。CodeBuddy 不再新增适配和授权路径；历史配置查看、拒绝、撤销、卸载及旧证据仍按现有安全规则保留。目录清理不删除兼容恢复代码。

Windows native/WSL2 分列仅适用于实际存在且属于产品范围的运行形态，不代表 WorkBuddy 提供 WSL2 版本，也不把 WSL2 中宿主成功当作 Windows 原生成功。

### 6.2 每个 OS 入口包含什么

初期各目录只需 `README.md` 与必要的运行/验证说明，不提前创建空壳框架。包含：

- 实测环境、架构、最低版本已知/待确认状态。
- 安装、升级、后台生命周期与保留数据退出说明。
- 各宿主接入方式、已保护路径、限制和诊断步骤。
- 到实际生产代码、现有验证脚本及证据的相对链接。
- 原生桌面验收、离线验证、构建验证各自入口。
- 维护者职责与当前在研任务链接。

未来如提供 OS 专属包装脚本，只做参数和环境适配，调用原实现；不复制签名、迁移或策略判定。

各平台页首先分流“安装已签名版本”和“从 main 开发构建”，安装步骤统一引用[签名包指南](signed-release-packaging.md)，不各自复制完整验签命令或维护一套公钥。0.3.0 包内 `INSTALL.md` 已补齐空状态首次启动；不能把 README 已更正误写成 bootstrap 的 `serve` 已自动初始化。发行标签、文件名、体系结构与验收等级在同一入口展示。

### 6.3 不迁移的 OS 实现

`apps/agentshield/cmd/agentshield/` 中 systemd、launch-agent、Windows Task Scheduler 逻辑和相邻 PowerShell 资源先保留。`internal/state/`、`statefs/`、`stateformat/`、`adapterinstall/` 的平台文件留在同包，遵循 Go 文件后缀与构建约束。

不能将所有 `*_windows.go` 机械移动到 `platforms/windows/src/`：这会改变 Go 包、内部可见性、测试上下文和嵌入资源路径。

### 6.4 DGX Spark 与 OpenShell

保留 `deploy/dgx-spark/` 作为硬件环境部署入口，Linux 平台页链接它；保留 `internal/openshell/` 和现有兼容脚本作为后端实现，不将 OpenShell 建成第四种 OS。

OpenShell 专题导航同时覆盖本机 Go 的 `apps/agentshield/internal/openshell/`、企业 Python 的 `apps/control-api/app/adapters/openshell/` 与 `app/openshell_sync.py`，关联共享合同和各自验证；不为目录统一而合并两条控制面实现。

记录至少区分：SIQ 候选、宿主版本、OpenShell CLI/网关版本、GPU/CPU 与实际使用模式、策略读回、加载确认、行为验证、远端停止能力、性能协议。本机 DGX 上的 CPU fixture 不升级成 GPU 推理或完整网关验收。

### 6.5 共享核心变更与宿主版本的交付映射

平台入口还应链接“共享修改 → 各 OS 所需复测”清单。目前共享审批/SEC 复查、Web 会话世代及内嵌资源、安装持久身份等变更已进入主线；Linux 的通过结果不关闭 macOS/Windows 的原生复测。Windows 资源解释与文件观察规格也不能被通用 Unix 路径说明覆盖。复用 [Linux 交接](linux-dual-host-platform-handoff-20260918.md)中的影响矩阵，并由新索引标明后续 Windows 集成已替代的旧状态，不复制另一份完整规格。

[OpenClaw 受控入口](openclaw-controlled-start-linux-20260919.md)及 `scripts/openclaw-controlled-start.py` 属于真实使用/复现工具，不能因“研究”命名直接搬入纯文档目录。登记 2026.5.12 与 2026.9.4 两套上游包、Node、补丁与复制体摘要，以及 `patches/openclaw/` 许可和适配器依赖；原版缺少最终检查点与受控副本通过同时保留。未来升级先新增版本配置和对应验证，不覆盖旧固定指纹，也不自动改变共享安装。

## 7. 测试、评测与第三方记录

### 7.1 三层分工

### 7.2 统一测评索引

先建立小规模人工可审查目录；字段确定后再做轻量校验器，不先造完整测评平台。

建议字段：记录 ID、类型、作者/组织及关系声明、source SHA、dirty 状态、制品/语料/验证器/脚本摘要、OS/架构/运行形态、宿主及后端版本、方法级别、预期与实际结果、精确分母、失败/中断/重跑记录、限制、公开证据路径及摘要、复核状态。

增补当前材料已经需要的区分：`implementation_candidate`（实际实现/二进制）、`evidence_commit`（证据纳入提交）、`integration_commit`（主线集成提交）各有独立字段；dirty 候选链接原逐文件源摘要，不能凭后来的提交补造当时的 clean SHA。发行记录另外关联 `release_tag`、tag 指向的源码、包/二进制/清单摘要、`packaging_tool_sha256`、构建工具版本和独立发布回执；main HEAD、tag 源码与制品摘要不得相互替代。`is_latest` 是查询时状态，不是版本永久属性。CI 记录保存工作流/run URL 与源码 SHA，五条工作流不改写成五项测试，也不与历史 31 项必需检查合并分母。另记录 `host_mode`（原版/固定补丁/模拟）、`model_mode`（fixture/真实模型）、自动化或人工操作、`supersedes` 与仍有效的具体范围。OS、架构、宿主/Node/后端版本不压缩成单个“平台”字符串。

**这是仓库索引的候选格式，不是新的运行时合同。** 不擅自改写现有 QA schema；需要互通时先明确版本与映射。

对历史记录无法取得的字段使用 unknown/not_recorded，并记录原因，不补造候选、时间或独立性。

### 7.5 将一次性发行验证沉淀为可复用工具

当前 `scripts/release/` 只有 `package.py` 与 `test_package.py`；CI 已运行八项打包边界单测，但最终包 14 项验证和远端八资产回读的驱动仍是本机 `.tmp/releases/` 下的临时脚本。保留已归档结果，同时把“下次可重复执行”列为 RA-03 的独立交付，先审查并参数化，不能直接提交含本机路径、临时状态或固定端口的脚本。

建议将检查分成三个显式阶段，沿用现有验签器，不另写密码实现：

1. 离线验包：可信公钥、Skill 实际内容、四目标 pin/大小/URL/版本、文件清单、许可、路径逃逸和执行位；篡改与缺清单必须拒绝。不启动服务、不需要私钥。
2. 本机安装链路：明确启用后在独立私有状态目录和可用端口执行包内首次启动、状态、配对、控制台、停止；失败也清理本测试服务。其他 OS 缺环境就保留未运行。
3. 发布后回读：按准确 tag 查询并下载到新目录，与已验证候选比对全部资产、tag 源码及公开下载 URL，生成新的公开回执；该工具本身不上传、不修改 Latest、不覆盖旧回执。

普通 PR CI 可做离线检查、失败样本与未签名构建准备；正式发行密钥不进入 PR、npm 或 Go 构建环境。正式包验证、真实安装测试、上传发布分别保留明确边界。0.3.0 的成功结果是回归样本，不能把下次同名命令返回零直接视作所有平台验收通过。

先枚举被 SHA256SUMS、manifest、签名及报告相对路径引用的文件，再判定能否移动。默认将历史 evidence 目录视作冻结集合，包括 `docs/evidence/releases/` 中已归档的本地验证、SOURCE-INFO、校验和、发布回执和源码 CI 记录。冻结约束是保护已有字节，允许在新的版本/记录路径追加经过审阅的结果，不能把整个 evidence 根目录理解为禁止今后新增证据。

索引更正、审查结论和“被后续结果补充”的说明放在新记录中，附所更正对象的原摘要；不就地美化失败记录，不用重新计算旧清单掩盖变动。

当前产品改动会要求新的候选验证，但不会抹去旧候选证据的历史效力。

本次只读复核 `docs/research/claims-evidence.json` 的 10 条证据 SHA-256 引用，10/10 与当前文件一致。其范围包括 `docs/hackathon/final-submission-state.md`、`benchmark-report.md` 和 `evidence/INDEX.md` 等看似普通说明文：这些文件同样不能直接追加迁移提示。本次未重新验证仓外归档、视频或完整历史验收。

冻结识别还须扫描证据目录以外的摘要消费者：历史发行 fixture、研究 JSON 台账绑定的原任务书、source-binding 清单、补丁指纹及相邻内嵌资源。不得仅用文件夹名称判断“普通文档可改”。新增更正记录可以指向已有纠正版本，但须保留原版本与原因，不借整理之名统一换行或重写旧日志。

### 11.2 大文件策略

文献全文约 131 MB、docs 跟踪内容约 120 MB（十进制），足以值得做体积盘点，但本次没有测量 Git 历史膨胀或 clone 成本。

先确定许可、下载频率、离线复现需求和长期托管方式，再选择普通 Git、按需外部获取或 Git LFS。首轮不进行历史重写、不批量引入 LFS、不删除 PDF/截图/日志。

若未来转外部存储，必须保留稳定获取说明、内容摘要、版本、许可和不可用时的明确状态。当前客户端二进制已使用 Release 资产分发；后续继续此边界，不复制到 Git、research 或 evaluations。新版本发布仍是独立动作，目录优化本身不触发自动发布。

### 11.3 私有边界

公开测评目录不保存 daemon 完整状态、signing.seed、配对码、token、模型配置、真实客户原文或未审查截图。新运行默认输出到隔离私有目录，审查后只发布必要材料。

目录 ignore 是防误提交机制，不是权限隔离。Linux/macOS 私有权限和 Windows ACL 分别验证，不能用 POSIX 0600 推断 Windows 私密性。

已有签名原文含敏感信息时，不能直接改正文再声称原签名有效；应隔离原始材料，生成有明确派生关系的公开摘要，并注明哪些验签能力无法公开提供。

## 14. 迁移执行与回滚协议

每个迁移 PR 必须包含：

1. 基线 SHA、明确路径集合、迁移前后映射、保留理由和排除范围。
2. 入链与消费者清单：文档、构建、CI、脚本、许可、工具、历史外部引用。
3. 冻结证据识别结果与迁移前摘要；冻结对象不改写。摘要从 PR base 读取并比较，不能同一 PR 同时改文件和“期望摘要”自证通过；新的冻结记录通过单独新增条目登记。
4. 先使用 Git 可追踪移动，避免同一 PR 大段重写正文，方便区分移动与语义变化。
5. 保持启动命令、状态格式与默认行为；若无法保持，拆出独立兼容变更。
6. 迁移后校验、失败/跳过项、恢复方案和维护者复核结论。

执行前后复核 base/head 和目标文件源 blob；其他窗口改变了同一路径就重新审查受影响项，不套用过时迁移清单。导航/指南回退只影响新 main，不撤销 Release、不覆盖旧包。若未来包的签名载荷变化，必须新候选、新摘要、新验证；目录 PR 不捆绑重新发行。

若导航失败，回退该导航提交；若生产路径变更导致运行失败，撤回该批变更并恢复旧入口。不要通过恢复旧版本覆盖用户运行状态，也不要把 `git revert` 当作状态格式自动降级工具。

任何跨平台文件名应避免仅大小写不同、Windows 保留名、尾点/尾空格等冲突；检查路径长度和实际支持的特殊字符。脚本引用全部采用正确引用/转义，不将绝对私有 HOME 路径写成通用入口。

## 16. 风险与选择

| 风险 | 应对决策 |
| --- | --- |
| 目录更整齐但安装命令失效 | 运行入口优先稳定，迁移命令单列验收 |
| 多个“current”继续互相冲突 | 一个当前导航，旧件仅兼容或历史 |
| 实验报告被当成生产能力 | 类型、候选、方法和限制随结果展示 |
| 大文件移动导致克隆问题未改善 | 先测 Git 历史和需求，不以工作区大小直接决定 LFS |
| 平台目录演变成三份核心代码 | OS 入口与核心实现分离，模块职责不变 |
| 新结果目录漏掉秘密忽略规则 | 先补防误提交规则与负向，再开放写入 |
| 清理旧 CodeBuddy 时破坏安全退出 | 保留历史查看、撤销、卸载及兼容拒绝能力 |
| 共享核心/残余平台工作被结构调整打断 | 基于已合入 main 逐路径协调；跨 OS 复测与源码搬迁分开安排 |
| 旧工作树被误认成最新源码或全部冗余 | 区分已吸收、已替代、独有和待核；保留未提交资产，不整树覆盖 |
| 历史验签 fixture 被重新分发为修复包 | 明确开发源码/历史样本/新发行三类身份及安装入口 |
| 已发布 0.3.0 被搬迁或说明修订覆盖 | 保留 tag/附件/回执；修订 main，后续需要发行时使用新身份 |
| 首页已更新但旧操作文档继续误导 | RA-01 对 AGENTSHIELD/安装指南/current 做入口一致性检查；Skill 改动独立成批 |
| 构建工具单测被当作最终包/平台通过 | 八项单测、14 项包检查、八资产回读、五工作流和原生验收分别登记 |
| 新研究命名覆盖原贡献与许可 | 保留作者、原始来源、授权范围和 Git 历史 |

暂不采用：拆为多个独立产品仓；统一重写所有测试框架；按 OS 全量拆包；创建并行权威合同；批量清除历史日志；强制重写 Git 历史；把一切“测试通过”折算成总体完成百分比。
