### 3.5 已核实的 OpenShell CLI 能力边界（**对 D01/D03 停止语义有决定性影响**）

`openshell sandbox` 子命令全集：`create` `get` `list` `delete` `exec` `connect` `upload` `download` `ssh-config` `provider`。

**由此得到的硬约束**（写进 D01/D03 设计，不得绕过）：

1. 任务书 §6.2「停止请求必须绑定任务操作身份…杀掉本地 CLI 不等于沙箱进程停止」在**当前 CLI 能力下无法由远端确认**。
2. 因此 E08（停止/恢复）预期为 `partial` 或 `blocked`；只设计保守状态，不承诺「任意后代进程停止」或「exactly-once」。
3. 停止**绝不允许**用「删除整个沙箱」替代（任务书 §4.6）。
4. `openshell logs --source sandbox` 是唯一可用的**只读**远端观测通道，可用于对账，但不可证明任务级归属。

**关键设计决策（据实记录，不虚构接口）**：

1. **独立操作种类**：`command = "siq-openshell-task-exec"`；既有 `/v1/openshell/session-executions`（`scope=policy_apply`、`task_executed=false`）语义**完全不变**，不静默升级。
2. **任务执行不写策略**：执行前需读回证明生效策略修订+摘要 == 批准值，否则 `openshell_task_policy_not_loaded` 拒绝；不自动 apply/repair。策略副作用与任务副作用分账。
3. **状态机不含 `stopped`**：CLI v0.0.83 无 stop/kill/cancel，`sandbox exec` 无 detach；`stop.remote_stop` 恒 `unsupported`、`remote_stop_confirmed` 恒 `false`（schema `const` 强制）。E08 远端确认腿预期 `partial`/`blocked`。
4. **不确定不可洗白**：`uncertain` 只能由管理员对账收敛，不得自动变 `failed`/`succeeded`/`denied`，也不得反写成"从未执行"。
5. **超时主界**：后端 `--timeout` 为主、本地有界 runner 为兜底，记录 `timeout_bound_that_fired`；**两者都不证明远端已停**。
6. **拒绝凭据注入**：不使用 `--env`（客户端可选凭据向量）；argv 始终带 `--` 终止符；不拼接宿主 shell。
7. **权限矩阵**：执行/状态/停止 `capDecision`；预览/对账 `capAdmin`。新 `capDecision` 路由须注册进 `isDecisionPath`，且 body 必带顶层 `platform`/`agent_id`/`session_id`（`decisionTuple` 依赖）。

### 11.4 关键实现决策

1. **批准语义由服务端重算，而非采信提交**：`canonicalTaskParams` 由「live 签名态（活跃 grant + 权限摘要 + 后端指纹 + 读回的策略修订/摘要）」重算，再与提交的 `params` 做**字节相等**比较。测试里的 `params` 是**另写一份**、不调用 `canonicalTaskParams`，避免自证。
2. **两层漂移检测**：
   - 边缘门（占预留之前）：只比对签名态，**不读网关**，因此一个仅仅过期的客户端不会烧掉人工批准；
   - 执行前门（`ExecTask` 内、派生之前）：`ReadEffective` 读回真实施行策略，修订或摘要漂移即 `task_policy_not_loaded` → `TaskStateRefused` → HTTP 409 `execution_refused` + `execution: not_occurred`，可自动对账为 `cancelled`。
   - `RecheckReservedExecution` 只处理引擎侧撤权/过期。
3. **`isDecisionPath` 的取舍**：该函数**仅被 `server_test.go:130` 的 `call()` 夹具引用**（`grep -rn isDecisionPath --include=*.go` 只有定义处与该引用），生产鉴权走 `s.mux` 的 `s.auth(handler, caps...)`。若把新路径**排除**在表外，`call(..., token, ...)` 会静默把 `token` 换成 `s.bootAdmin`，任何 401 断言都会为错误的原因通过。故**显式登记**，并在函数上补注释说明；同时新测试仍用专用 `taskExecPost` 逐字传递 bearer。
4. **公开合同版本 ≠ 引擎版本**：边缘接受 `openshell-task-execution-request/v1`（合同冻结值，Python 侧同断言），在 `ReserveHoldExecution` 之前一次性转译为 `hold-execution-reserve/v1`。不改合同、不改测试。
5. **形状门不得严于合同**：合同 `network_targets` **无 `minItems`**，故形状门允许空列表（授权范围另由 grant 决定）；此前若拒绝空列表即为「边缘门比协议更严」，已修正。
6. **参数与证据的分工**：原始 `argv` 只存在于 `params`（人类批准的正是这条命令）；**全部**证据/观测/审计记录只存 `argv_digest` + `argv_count` + 输出字节数/摘要。测试对 outcome 与 plan 两份记录都断言「不含任何原始 argv 片段」。
7. **落盘先行**：预留在前，随后写 `ostp-` 计划记录（D03 重启对账所需：预留回执只存 `ParamsDigest`，**不含参数本体**），计划写入失败即拒绝执行。结果记录 `ost-`。
8. **`execution_uncertain` 的据实语义**：非零退出与 CLI 侧失败**无法区分**，故 `TaskStateFailed` 一律 `execution_uncertain: true`（处理器内有注释明确「不要改成 `outcome.ExecutionUncertain`」），且**不**自动对账、**不**重放。只有 `PreflightRefused`（派生之前即被拒）才是可证的 `not_occurred`。

   - **P8 停止记录严格先于动作**：链校验 → 归属校验 → 读证据 → 读本地观测事实 → **先写停止记录** → 才 `StopLocalTask`。记录写不下 ⇒ 503 `stop_not_recorded` 且不发动作；本进程未观测到 ⇒ 409 `stop_not_observable` 且不发动作。
   - §5 第 2 条补 P8 交叉引用，并明确 **D03 未新增任何远端停止能力**，该腿保持 `partial`。

### 12.5 测试证明的负向事实

- **读路由的 200 不代表任务成功**：成功读到/写下状态就返回 200，`state` 才是结论。
- **不发明状态**：投影**没有**顶层 `task_executed` 字段；成功只由 `state: succeeded` + `remote_exit_code: 0` + `output` 表达。任务书禁止把控制面成功报告成真实执行成功，这条断言就是它的回归防线。
- **不存在即不属于你**：`status` 对未知预留与外来预留返回**同一个** 404（存在性不泄露）。
- **篡改链不降级**：链被改动 → `openshell_chain_unverified` 503，**不会**被读成「任务从未发生」。
- **对账只结案不重放**：成功对账返回**重读后的状态投影**，`reconciliation_receipt_id` 以 `-rec` 结尾并绑定预留；重复对账幂等；**反向结论 → 409 冲突**，不覆盖既有观测。
- **停止永不删除沙箱**：`delete_sandbox` 恒 `false`，`remote_stop: "unsupported"`、`remote_stop_confirmed: false`。
- **老预留不可混用**：`policy_apply` 的预留被拒绝对账，防止按名字把两种操作混淆。

### 14.2 缺陷 F-1：`policy_read` 的第二个位置参数是**沙箱选择器**，不是描述

- `policy_read(step_id, target=None)` 构造的是 `openshell policy get <target or self.target> --full`。
- `leg_e02_window` 的 `finally` 里写的是 `self.policy_read("E02z", "post-window policy state for the record")`，于是**散文被当成沙箱名**送给 CLI：`Error: × code: 'Some requested entity was not found', message: "sandbox not found"`，rc=1（47 ms）。E02z 记 `fail`；抛出的异常命中外层 `except`，E02z5 记 `fail`（**这不是第二个缺陷**，是同一处的连带）。

### 14.3 缺陷 F-2：E09 去对账了一条**永远不可能存在**的预留

- 回执链命名约定（本轮实测确认）：每个决策回执 `rcp-<hex>-<HHMMSS.ffffff>` 都有一个 `-res` 兄弟（`hold_resolution`）；**只有真正被提交过的任务**才有 `-exec`（`record_type: "hold_reservation"`）与 `-exec-obs`。
- 旧 E09 用 E09j 的 `decision_receipt_id + "-exec"` 去查链，而 E09j 是"批准但从未提交"，因此该回执必然不存在 → `_reservation_hash` 抛 `StepFailure` → 整条腿 ABORT。服务端本来也只会回 404 `openshell_task_reservation_unknown`。
- 重写：对账矩阵改为操作 **E09a 那条真正被崩溃孤儿化的 `-exec` 预留**（链上有 `hash`、无 `-exec-obs`），把"从未提交的批准"改造成一个**显式的 404 拒绝用例**，并把所有拒绝用例排在闭合（200）**之前**——否则闭合之后的拒绝与"已对账过"不可区分。
- `outcome` 绑定到**独立读回的远端效果**（不是执行器自述）；闭合后再回读一次投影。

### 14.4 E09i 的 `partial` 是读取时序伪影

E09h 的回读发生在远端 argv 的 30 s 睡眠中段（约第 9 秒）。单次采样记 "absent" 与"效果从未落地"不可区分。改为**有界轮询**（上限 150 s，记录 `read_back_attempts`）。

### 14.5 缺陷 F-3：E05 的计数器夹具用的是**沙箱内不可读**的 `/dev/zero`

- 实测（健康窗口，0.182 s，rc=0）：
  `sandbox exec -n siq-o05v6-taskexec-002524 --no-tty -- /bin/sh -c "dd if=/dev/zero of=/tmp/o05v6-pc.bin bs=1 count=1 status=none; echo dd-done"`
  输出：`dd: failed to open '/dev/zero': Permission denied` + `dd-done`。
- E05 的 argv 是 `dd if=/dev/zero of=<counter> bs=1 count=1 oflag=append conv=notrunc status=none; wc -c < <counter>`。`dd` 打不开输入 → **计数器文件从未被创建** → `wc -c < <不存在的文件>` 让 shell 以重定向失败退出（**exit 2**）。这与 E05d 记录的 `exit_code: 2` 完全吻合。
- 因此 E05d 的 502 **是夹具失败，不是产品失败**；并发声明本身仍由 `E05c.concurrent-results.json` 支撑（1 个赢家 + 3 个 409 `hold_execution_already_reserved`）。
- **未复现项（`unresolved`）**：E05d 记录的 187 B stderr（`e48cf19ed9bc041217a34323735f11b5cc694b7505140d18428e9c7bf80c6eae`）**未能**再采样到同一摘要——见 14.6，该 argv 目前一旦执行就会让沙箱 exec 通道停摆，无法重复测量。**不主张**它等于任何一条已知错误文本。
- 顺带确证：E01 记录的 53 B stderr（`76ec9768ba15ab3ee78d1bd1bc79b8b2788d2eb20095b51908d40003018fe287`）= `"/bin/bash: /home/sandbox/.profile: Permission denied\n"`，是**每一次** sandbox exec 都会产生的常量噪声（本次探针逐字复现），与 E05d 的 187 B 无关。

### 14.6 环境级发现：`sandbox exec` 会间歇性停摆，且 `--timeout` 不约束它

观测序列（全部为本批自有沙箱 `siq-o05v6-taskexec-002524`，`sandbox list` 全程 `Ready`）：

| 观测 | 结果 |
|---|---|
| `sandbox exec ... /bin/echo hi`（健康窗口） | rc=0，**0.14–0.23 s**，stdout `hi` |
| 同上，连续 3 次（健康窗口） | 3/3 rc=0 |
| E05 那条 argv（`dd … oflag=append conv=notrunc …; wc -c < …`） | **停摆**，本地 `timeout 40` 击杀，两路输出均 0 字节 |
| 紧随其后：`echo hi` / 写重定向 / 读重定向 / `cat` / `printf` **全部** | **停摆**（15 s 上限内无一返回） |
| 又过约 3 分钟后再探 | `echo hi` **恢复**，0.14 s |
| 再跑一次 E05 argv | **停摆**；其后 6 次探针（含 `echo`）全部停摆 |

- **`--timeout 20/30/45` 均未触发**：CLI 自己的超时在停摆时不起作用。
- 本地击杀 CLI 之后，**远端会话的结局不可知**——这正是 D02 执行器头注释所声明的诚实边界，本机由此得到一份**组件级**观测。
- **自我更正**：本段早前曾把停摆归因于"远端 argv"（`dd … oflag=append conv=notrunc`）。该归因**过早**：停摆窗口内 `echo hi` 也同样停摆，说明停摆是沙箱 exec 通道的**状态**，argv 只是最常被牵连的触发场景。两种假设（argv 特化 vs. 周期性复发）**尚未区分**，正在用后台 `echo` 心率探针测量恢复窗与自发复发。

### 14.7 对 D05 计划的影响

- base driver 的 `cli()` 用 `subprocess.run(timeout=180)`；停摆时一次调用最坏**占用 180 s**并击杀本地 CLI。若验收运行里出现多次停摆，整轮会显著拉长且相关腿按设计转 ABORT——这属于**环境条件，不是产品失败**，必须与产品缺陷分开记账。
- 后续动作顺序：(1) 后台心率探针测恢复窗；(2) 在健康窗口复核 E05 的替代夹具（`printf x >> <counter>; wc -c < <counter>`）；(3) 再整体重跑 D05 验收，把停摆引发的失败单独标注。

### 14.8 停摆容错落地（base driver 改动）

针对 14.6 的通道停摆，对**夹具层**（不是产品层）做了三处改动，原则是"停摆要留下证据，且绝不被误当成远端结论"：

1. `StepFailure` 之下新增 `CliStall(StepFailure)`：语义是"本地边界到了，远端结局不可知"。
2. `cli()` 增加 `timeout` 形参（默认 180 s），并把 `subprocess.TimeoutExpired` 由**未捕获崩溃**改为**记录一条 `status=fail` 的证据条目**（含 `local_bound_s`、`exit_code: null`、说明文本"被杀死的本地 CLI 不是远端停止"），随后抛 `CliStall`。
3. `sandbox_exec()` 增加 `timeout`（默认 90 s）与 `retry_stalls`（默认 `False`，`stall_attempts=3`）。重试**只在 `CliStall` 上触发，绝不在非零退出上触发**——停摆的写可能已经落到远端，盲目重放会写两次。因此只有**幂等只读**命令显式选择加入：base driver 的 `K03a`（`cat /proc/net/route`）、`K03b`（`printf`）、`K35a`（`cat` 回读金丝雀文件），D05 driver 的 `D00a`（读路由表）、`read_sandbox_file`（`cat` 回读）、`sandbox_path_exists`（`test -e`）。所有写类夹具（E02x/E05x/E07x/E09x 等）保持**单次执行**。
4. `await_exec_ready` 的单次探测上限由 150 s 降到 45 s，使 420 s 的等待窗内能容纳更多次重试而不是被一次长挂吃满。

**边界声明**：这些改动只影响验收夹具的健壮性，不改动产品代码路径，也不改变任何一项验收的判定标准；一次停摆引发的腿失败在报告中一律标为**环境条件**，与产品缺陷分开记账。

### 14.13 E02 不可达的根因：沙箱拓扑与 egress 代理（环境级，已定性）

`leg_e02_window` 曾 ABORT 于 `both targets must be reachable first: A=502 B=502`。逐层定性：

3. 沙箱只有两个接口：`lo` 与 `veth-s-1ef544ee@if4`（10.200.0.2/24），**没有 eth0**；默认路由 `via 10.200.0.1`，唯一的另一条是 10.200.0.0/24 直连。`http_proxy=http://10.200.0.1:3128`（及 HTTPS_PROXY/ALL_PROXY/…），`no_proxy=127.0.0.1,localhost,::1`。
