# 07 · 预览工具改「身份 id 来自算子授权目录」——合成闭环 + 负对照（2026-09-26）

本文件留痕 R09.16：修 `scripts/enterprise-experience/openshell-preview-live-check.py`，
使它的身份 id 不再运行期现造、而改从**算子预先声明的授权目录**读取。承接本目录 §五
（该工具在 `require_target_authority` 生效后**结构性**无法通过预览断言）。

**本文件里没有任何真实网关、真实 CLI、真实沙箱或真实策略。** 全部观测来自一个合成
`openshell` 可执行文件（只打印固定 `gateway info` / `status` / `policy get` 文本，从不联网）
与一个合成授权目录。因此：

- 天花板仍是 `readback_verified` 之下——本文件**不产生** `enforcement_verified`；
- 合成跑法下结果里的 `real_gateway: true` 是**工具里的常量字段，不是检查项**，
  不得当作"真的连过网关"的证据（工具自身未校验这一点，本轮也没改它）；
- 本文件不构成 E149 的字面复现：见 §六。

## 二、为什么必须改（不是"放行一个环境变量"）

`app/target_authority.py:125-133` 对授权目录做**精确元组相等**判定：

```text
(tenant_id, environment_id, asset_id, agent_instance_id,
 endpoint_fingerprint, gateway_name_sha256, backend_target_id)
```

`environment_id` 原先由 `POST /environments` 服务端生成，`asset_id`/`agent_instance_id`
由工具在运行期 `flush()` 生成——算子**不可能在运行前**写进目录。所以只把变量加进白名单，
只会从"变量被清掉"变成"目录里找不到这条授权"，预览仍是 409。

## 三、实现要点

1. **读目录**：复用门禁自己的 `_read_authority_bytes` + `_unique_object` + `TargetAuthority`，
   而不是另写一套——两套判定必然漂移。符号被改名会立刻 `ImportError`（响亮失败）。
2. **选条目**：`--assignment-id` 精确指定；否则按 `backend_target_id == --target` 取唯一一条。
   缺条目 → `authority_target_absent`；多条 → `authority_target_ambiguous`（同一沙箱目标在两个
   XDG 上下文各有一条授权，是真实形态）。
3. **核对指纹**：`probe()` 后比对 `caps.endpoint_fingerprint` 与
   `sha256(caps.handshake_gateway)`；不符即以 `authority_endpoint_mismatch` /
   `authority_gateway_mismatch` 失败，并把**两个观测摘要都写进失败记录**，算子一次就能补齐目录。
4. **落库**：`Environment` / `AgentAsset` / `AgentInstance` 按条目里的 id **显式主键**直插隔离库
   （`POST /environments` 不接受算子指定 id）。代价见 §七。
5. **失败留痕**：`write_failure()` 只写固定判别码与摘要，`production_eligible` /
   `runtime_policy_mutated` / `enforcement_verified` 恒为 false。

## 六、新发现：「目录变化拒绝旧预览」的**断面**已经换了

原工具在 `XDG_CACHE_HOME` 变化后提交旧摘要，期望 409 `deployment_preview_changed`。
在本候选上实测得到的是 **409 `deployment_target_authority_unverified`**：

- 上下文一变 → 调用指纹随之改变 → 授权目录里的条目不再匹配 → `_prepare` 内的
  `require_target_authority` **先于**摘要比对失败；
- `deployment_preview_changed` 在 `app/routers/deployment_preview.py:252`，本路径**不可达**。

性质（"上下文变化必须被拒，且零写入"）仍然成立，被拒的**位置更靠前**。因此工具把检查项从
`changed_context_refuses_old_digest_without_writes` 改名为
`changed_context_refused_without_writes`，并把实际判别码写进
`changed_context_detail`，不假装机制还是旧的；隔离测试钉住这一断面。

**对 E149 的影响**：`docs/development/ux-openshell-live-preview-e149-validation-20260923.md`
记录的 8/8（"目录变化拒绝旧预览"，前后 revision 均为 2）**即使授权目录完全正确，也不可能
逐字复现**——那条断言的观测码必然是授权闸的码。E149 的**性质**可复现，**字面记录不可复现**。

## 七、本轮**没有**证明什么

1. **没有碰真实网关。** 合成 CLI 之下，`real_gateway` 字段仍是 `true`（工具常量），
   这正说明该字段不能当证据用。
2. **没有恢复真实网关上的 E149。** 要真跑，必须有**算子签发**的授权目录条目
   （含真实的 tenant / environment / asset / agent_instance / 指纹 / 网关名哈希）。
   由本轮执行者代签等于自己制造一份授权，属于越界——因此停在"工具已就绪 + 需要算子条目"。
3. **没有**任何 `enforcement_verified`、没有真实 deny 观测；`expect_deny` 仍是固定兼容样例。
4. **没有**验证 E149 之后**其余**环节在真实网关上的可达性：合成 bench 证明的是这条链路
   在替身上可达（10/10），真实网关上的 `plan_change` / 读回是否同样通过，仍未实测。
5. 环境创建这一支不再经过 `POST /environments`（该端点不接受算子指定 id）；
   若以后要求"必须经由环境创建 API"，需要另想办法让服务端接受预声明 id。
