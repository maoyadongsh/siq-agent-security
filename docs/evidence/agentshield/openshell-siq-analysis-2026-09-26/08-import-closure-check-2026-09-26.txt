§0 这份留痕的边界（先读）
--------------------------------------------------------------------------------
- 本工具与 `enforcement_verified` **无关**：它不碰强制点、不产生行为证据、不使任何门禁变绿。
- 它对**真实仓库只读**：`git archive <ref> apps/control-api | tar -x` 到**临时目录**，在临时目录里
  反复试导入；不写仓库内任何路径、不切换共享工作树、不提交、不改分支。
- 子进程环境是**白名单**（`PATH/HOME/LANG/LC_ALL/TZ` + `PYTHONDONTWRITEBYTECODE=1` +
  `SIQ_AS_DEV=1` 合成 dev 身份 + `PYTHONPATH` 指向临时树）；不读 `.env`、私钥、种子、凭据。
- 结论只说明「这个 ref 的导入面是否自足」，**不是**发布授权、**不是**「源码已冻结」、
  **不是**「该 ref 安全/可部署」。

§1 工具做了什么（`scripts/enterprise-experience/import-closure-check.py`）
--------------------------------------------------------------------------------
1. 解析 `--ref`（默认 HEAD）为 commit sha；
2. `git archive <sha> apps/control-api` 导出到临时目录；
3. 在只指向该临时目录的解释器环境里 `import app, app.main`；
4. 失败则从异常里判出「下一个要补的模块」，去**工作树**里定位该模块文件，拷进临时树，重试；
5. 直到导入成功 / 轮次耗尽 / 工作树也定位不到 / 判定"无进展"。

判别码刻意分成四种，**不许把不同原因混成一个"失败"**：
  - `import_closure_closed_at_ref`：该 ref 自身即可导入，**零补件**（最健康）；
  - `import_closure_open`：需补入若干**工作树**路径 → 这些就是「清单没覆盖到的闭包缺口」；
  - `import_closure_unresolvable`：缺的模块连工作树里都没有（补工作树文件也解决不了）；
  - `probe_environment_unsafe`：解析到的 `app` 不在临时树内（路径泄漏）→ 本次结论作废。

§5 构建这个工具时，它自己先错三次（如实留痕，不掩盖）
--------------------------------------------------------------------------------
1. **`from 包 import 名` 的两义性**：`cannot import name 'credential_rotation' from 'app.routers'`
   既可能是「包缺该符号」，也可能是「**该子模块文件没被提交**」。首版一律当成前者去补包的
   `__init__.py` → 补了也不解决问题 → 下一轮又判成同一件事 → **空转到轮次耗尽、补件数为 0**
   （首次实跑就是这样，结论 `rounds_exhausted`，且把 `rounds` 字段写成了整数）。
   修法：候选列表改为先试 `包.名`、再试 `包`，命中哪个补哪个。
2. **无进展必须立刻停**：同一份工作树文件再拷一次不可能改变结果。补入后若下一轮判定又要补
   **同一个路径**，立即以 `no_progress` 有界结束（带 `repeated_path` 与最后一行失败摘要），
   不许空转。
3. **独占目录的退出码**：`--out` 已存在时首版直接抛 `FileExistsError` 回溯（退出码 1，
   和"闭包开着"撞车）。改为固定 `out_dir_exists` + 退出码 **2**，并**不触碰**原目录。

另有一处**真实撞到过的坑**被做成守卫：探针解析到的 `app` 必须落在临时树内。构建期间有一次
命令因 cwd 未切过去，`python` 从 **cwd 下另一个可导入的 `app`** 里导入成功并打印 `IMPORT_OK`
——那是一次**假绿**。现在 `app.__file__` 在 `import app` 之后**立刻打印**（因此导入后续失败也
拿到它），不在临时树内即 `probe_environment_unsafe`、结论作废。
