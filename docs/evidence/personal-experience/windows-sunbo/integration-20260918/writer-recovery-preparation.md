# Issue #79 Windows 探测准备

目前未修改生产 Writer，主修指定问题已单独提出。实机探针只操作自有子进程，OpenProcess 仅申请 SYNCHRONIZE，句柄不可继承，WaitForSingleObject 超时0：运行时返回258；正常退出0后，同一已持有句柄返回0；释放本批句柄后重新打开该PID仍成功，但返回0（进程已终止）。因此不能把 OpenProcess 成功或PID仍可打开当作存活，必须检查进程对象是否已终止。无强杀、无后台服务。

拟议实现边界：OS专属文件，非Windows保留原行为；Windows严格检查PID范围避免uint32截断，最小访问权和零等待，仅明确已终止或明确不存在才报告死亡，访问拒绝/未知错误/未知等待码保守busy。释放所有已打开句柄。不得申请终止进程权限，不检查其他用户秘密或关闭安全防护。

必需负向：活进程/当前进程拒绝接管；伪造或越界PID不截断为另一PID；访问拒绝与等待失败拒绝接管；句柄关闭；新锁/foreign owner不可释放。正向：真实子进程终止后旧锁隔离、恢复、WriterHeld一致。保留旧行为失败证明。

共享接管路径也需审阅：当前 readLockFile→processAlive→Rename 的读回与改名之间存在并发替换窗口；本次只是源码审查提出的风险，尚未构造确定性竞争证明，不能据此声称已复现第二个漏洞。主修实现需要验证并发接管不会隔离新持有者的锁，不能仅补存活探测后用单线程成功宣称恢复安全。

受影响回归：state、migration、commit recovery、生命周期 scoped Writer、30项Windows CLI，以及所有最低构建/Schema检查；之后用固定二进制做实际中断恢复。当前68/303计数不变。
