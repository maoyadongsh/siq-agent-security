# 风险处置真实并发：首次失败与修复效果

2026-10-06，作者侧本机执行。**旧候选120/124，修复候选124/124。**五组真实重叠的HTTP或到期任务，在独立PostgreSQL中使用可观测锁等待建立实验窗口。修复前四组失败，原协议、候选及全部失败数据保留。

## 发现的问题

风险接受接口已有行锁；解决和确认接口却先读取状态、之后才执行写入。发生竞争时两个请求可以同时基于旧状态通过检查，产生相互冲突的成功结果。到期worker同样可能让两个任务读取同一已接受风险，并分别追加重开审计和事件。

本批不是模型攻击实验，而是企业治理状态正确性的真实业务检验。风险台账必须与用户成功操作、到期时间和审计一致；只有接口返回200并不足以证明处置有效。

| 竞争组 | 旧候选001 | 修复候选002 | 外部判据 |
|---|---|---|---|
| 接受 / 接受 | 200 / 409 | 200 / 409 | 只有赢家的接受元数据、审计和事件 |
| 解决 / 解决 | 200 / 200 | 200 / 409 | 只保留一次解决，修复证据对应赢家 |
| 接受 / 解决 | 200 / 200，最终resolved | 200 / 409，最终risk_accepted | 状态与成功响应一致，不覆盖接受记录 |
| 接受先等待 / 确认 | 200 / 200，最终acknowledged | 200 / 409，最终risk_accepted | 已接受不可再确认或改写负责人 |
| 到期任务 / 到期任务 | 重开1 / 1、重复审计和事件 | 重开1 / 0、各一条审计和事件 | 原ID重开一次，owner及接受元数据保留 |

前四组先锁定目标finding，确认第一个请求出现PG锁等待，再启动第二个并确认两个不同PID等待后释放。实验固定了接受在混合组先入队，不能推断自然竞争中的赢家概率。

到期组通过专属审计触发器延迟到期事务提交，触发器不改数据或判定。首个worker已等待后启动第二个；修复后第二个在首个仍持行锁、屏障尚未释放时返回0，原始时间与输出核对通过。它表示本周期跳过被锁记录，不等于所有到期工作已完成，更不保证长期调度公平性。

## 修复与版本边界

001固定`5470ab3780f2-riskworkerfix1`；002固定`5470ab3780f2-riskracefix1`。解释器、依赖和测评/评分脚本摘要一致。产品仅在[风险路由](../../../apps/control-api/app/routers/findings.py)的确认、解决查询上增加行锁，并在[到期worker](../../../apps/control-api/app/worker.py)查询上使用`FOR UPDATE SKIP LOCKED`；新增[并发合同](../../../packages/contracts/enterprise-risk-concurrency.v1.md)及14项鉴权、终态与事务回滚回归测试。无数据库结构迁移，无历史记录清理。

鉴权仍按验证tenant定位对象后检查权限；状态、审计和outbox保留同一事务。接受后合法拒绝、审计写入失败回滚和既有时区行为均继续检查。四个并发失败反映缺少统一状态锁与到期领取的机制问题，不能直接当作四个独立安全漏洞。

## 业务入口与计数

真实Edge CLI/Hermes Connector采集专属配置→生产模式API/独立PG→确认原生资产→规则生成风险。每组使用不同finding ID；组间通过真实到期/解决API及规则再次命中取得下一ID，没有SQL插入或重置finding。风险条件为合成配置中的无effective权限，接受和重开不产生effective事实。

- 001：81项基座显式HTTP，额外19项HTTP（并发8、准备11），合计100；两个并发到期子进程及一个真实清理reaper。
- 002：81项基座显式HTTP，额外20项HTTP（并发8、准备12），合计101；两个并发到期子进程及三个真实清理reaper。
- 两批合计201项显式HTTP、8次真实reaper；原生Edge内部HTTP未独立计数。HTTP准备数差异由混合组最终状态不同产生，不是丢失请求。
- 模型推理0，新增自然攻击或独立确认任务0。强制重叠样本不用于计算自然竞态概率或性能吞吐。

主冻结评分器对到期单等待者的时序条件较宽；002预注册另要求补充检查第二worker确实在屏障释放前完成且返回0。该严格核对已经执行，未事后重写原评分器。未来同类协议应把这一条件直接纳入主评分，不能仅凭线程已启动或少一个等待者宣称并发成功。
