# OpenClaw approval execution checkpoint / v1

Status: local integration contract; not an upstream OpenClaw SDK feature. This
contract does not issue Intent authority or turn runtime metadata into policy.

## Producer and consumer

The host execution wrapper produces `approvalExecutionRecheckVersion: 1` in the
context passed to a `before_tool_call` handler. The value is a number equal to 1.
It must be generated by the host implementation that actually enforces the
checkpoint. Tool arguments, the tool event, plugin configuration and environment
variables are not capability authorities.

The SIQ adapter consumes this context field when its signed decision is `hold`.
Missing, malformed or unknown versions mean unsupported. In block mode an
unsupported hold is blocked before native approval begins. No fallback to the
older approval path is allowed. Existing advisory-mode failure handling applies
in warn/audit_only; those modes are not enforcement guarantees.

## Checkpoint callback

After local SIQ approval, the adapter returns its native `requireApproval` with:

```typescript
beforeExecute(
  finalParams: Record<string, unknown>,
  signal: AbortSignal,
): boolean | Promise<boolean>
```

The host invokes the callback after platform approval and before invoking the
tool, using the final merged parameters that will be passed to the tool. It
awaits the result. Only the boolean `true` permits execution. False, undefined,
other truthy values, thrown errors and rejected Promises veto execution. A
cancelled signal also vetoes, including when the callback returns true afterward.

The host limits the wait to five seconds, aborts the supplied signal when the
budget expires, and clears its timeout and external cancellation listener on
completion. An uncooperative Promise cannot keep execution eligible after the
budget. The existing non-awaited `onResolution` notification is not this gate.
If the host permits a timeout-based platform approval for another plugin, it
must still run that plugin's checkpoint; SIQ uses platform timeoutBehavior=deny.

The SIQ callback has a one-second budget and queries the existing
[hold-status request](hold-status-request.v1.schema.json) and
[response](hold-status.v1.schema.json) contracts. It supplies the original
platform/session/agent/tool/tool_call_id/action_id/decision_receipt_id and the
final parameters. It returns true only for a matching, current, unexpired
approved result and an uncancelled signal. It holds only the decision credential;
it cannot resolve the approval, sign authority, consume the action or extend TTL.

## Compatibility and limits

The host retains legacy behavior for other plugins that provide no checkpoint.
The SIQ adapter requires both the context capability and its actual callback, so
an unmodified host or old candidate without the marker cannot complete SIQ holds.
Ordinary allow/deny/redact mapping is unchanged.

This declaration is part of the trusted host/plugin execution boundary, not a
cryptographic attestation against hostile same-process code. The check is a
snapshot, not an atomic lease covering external side effects. It does not prove
the absence of mutations after the checkpoint, independent effect verification,
OS isolation or a real human's presence.

Acceptance requires both a successful native approval/execution control and
negative cases for unsupported hosts, revoked authority, altered final params,
exceptions, non-boolean results, timeout, cancellation and daemon disconnection.
See [integration verification](../../docs/trusted-intent-v2-approval-integration-20260907-221813.md).
