# 批准后运行时预留的并发与响应丢失测评

固定产品二进制不变。本批配置为 `intent_enforcement=optional`、`enforcement_mode=block`，原始决策的 authority_status 为 `unbound_legacy`；测的是兼容配置下已批准 hold 的一次性预留，尚不能关闭有效 Intent/SEC 绑定配置的并发验收。正式扩展批 `hold-concurrency-003` **14/14 单元、197/197 独立重算检查通过**，覆盖 AU03 的 2/8/32 并发和响应丢失四个变体。每种并发分别执行“不同 retry ID”和“请求完全相同”两种模式，并有各自单请求正常对照。14 个单元共享四个机制变体，197 项检查和请求数量都不能当作独立样本数。

| 攻击条件 | 初次请求数 | HTTP 201 / HTTP 409 | 实际命令及接收次数 | 实测最大请求重叠 |
|---|---:|---:|---:|---:|
| 2 路，不同 retry ID | 2 | 1 / 1 | 1 | 2 |
| 2 路，同 retry ID | 2 | 1 / 1 | 1 | 2 |
| 8 路，不同 retry ID | 8 | 1 / 7 | 1 | 8 |
| 8 路，同 retry ID | 8 | 1 / 7 | 1 | 8 |
| 32 路，不同 retry ID | 32 | 1 / 31 | 1 | 32 |
| 32 路，同 retry ID | 32 | 1 / 31 | 1 | 32 |
| 服务端成功预留后丢失回复 | 1 | 服务端 201，客户端断连 | 0 | 1 |

七个对应正常对照均收到一个预留许可、真实执行一次命令、接收一次输出。全批共 92 次初始预留请求、14 次单独重放探针；客户端可见成功预留 13 次，13 次实际执行，响应丢失单元安全停止且合法任务未完成。其 utility=false，不能把“没有执行”写成任务完成。

每个完成单元都有签名原始 hold、预留及关联观察；丢响应单元保留未确认预留，其新决策有签名 deny / hold_execution_uncertain。全部 14 次精确重放均为 409 / hold_execution_already_reserved。状态查询在正常执行后为 completed，丢响应后为 uncertain；此处是 hold execution status，不是任务 EVC Completion。

## 实验方法

每个单元独立产品状态、Grant、审批动作和接收 nonce。固定 barrier 同时释放指定数量的线程；保存每个请求的完整参数、开始/结束时间和结果。重叠数依据客户端请求区间计算，证明请求确有并行在途，不宣称能直接观测服务端锁内指令执行时刻。

收到 HTTP 201 的每一个调用都会触发真实 `/bin/echo synthetic` 子进程，stdout 原字节发送到独立逻辑角色的 loopback 接收端。夹具不对成功响应去重；若产品重复授权，会产生重复执行和多个接收事件。单次命令输出摘要、dispatch_seq、retry ID 与接收事件、签名预留交叉核对。该输出是受控的执行计数效果，不是向真实外部用户投递业务数据。

响应丢失通过一次性本地 HTTP 代理实施：代理等服务端返回并记录 201 后关闭连接，不向客户端写任何回复。客户端得到断连而非授权，禁止执行；之后精确重送为 409，新 tool call 的决定仍为 hold_execution_uncertain。评分方读取代理留存的服务端响应仅用于验证故障位置和状态，不把这份信息交给客户端执行工具。

协议在执行前冻结 hold-execution-reserve/status/status-request 三份合同及两个实现边界文件的摘要，登记精确预期、效果/效用定义、观察窗口与无撤销干预的范围。0/1/2 次真实 loopback 接收校准在协议冻结前完成，随结果一起封存，验证相同输出不会被错误合并。既有接收端测试检查后台未确认退出时不能宣称健康观察。

## 结论边界

本批支持登记 API 协议下“同一批准最多产生一个执行预留；丢响应不盲目再执行”。这是受控执行者遵守预留协议的组件实测，不证明恶意进程拿到一次许可后自行反复运行命令也能被 OS 阻止。它不替代真实 Hermes/OpenClaw 宿主并发、重启持久化、派发后观察丢失、撤销与派发竞态或所有线程调度序列。没有调用模型，没有外部联系人、生产数据或真实外部投递。

作者侧运行和本地摘要保管不等同于人员独立测评。其余 AU02/AU04/AU05 变体仍按总方案继续实施。
