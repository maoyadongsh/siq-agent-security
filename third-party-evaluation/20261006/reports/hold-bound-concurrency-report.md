# Required Intent 下的批准预留并发与响应丢失

本轮固定产品二进制不变，`hold-bound-concurrency-003` 在 `intent_enforcement=required`、block 模式下完成 **14/14 单元、239/239 判定检查**。原始签名决策均为有效绑定的 Intent v3，文件路径有签名 USER 来源；测试不再借助兼容模式的 unbound_legacy 授权。原生宿主与 SEC 调用上下文尚未覆盖，不能据此关闭整个 AU03。

## 注册与调用前提

每单元独立状态、会话、Grant 和任务。通过正式接口创建仅允许 `write_file` 的 Grant，调用 `require-approval` 收紧为人工审批，然后 challenge、approve、deploy。Intent 精确允许目标文件和 `file.write` 效果；路径来源 assertion 绑定同一 platform/session/agent/task 及实际路径摘要，不放宽默认信任要求。任务 ID 贯穿决定、状态查询、reserve、observe。

通用 `exec` 被产品识别为含未知效果，绑定 Intent 后会拒绝，因此本批改用可明确描述效果的 `write_file`。执行者对每一个客户端收到的 HTTP 201 都真实写入自有目录，不去重；记录写后摘要并将读取到的文件字节发送到独立接收角色计数。文件初始不存在，最终状态单独取样。多次相同写入即使最终文件字节相同，也会产生多个计数事件。

协议先冻结再执行，注册 reserve/status 合同、Intent v3 合同和相关实现文件摘要，保存 0/1/2 次真实接收的正负校准。攻击者只能竞争批准预留或丢弃响应，不能修改权威状态及观测器。观察窗口延续至所有竞争者、故障代理和重放/状态探针结束。

## 实测结果

| 条件 | 初次 reserve 请求 | 客户端 201 / 409 | 实际写入 / 接收 | 最大在途重叠 |
|---|---:|---:|---:|---:|
| 2 路，不同 retry ID | 2 | 1 / 1 | 1 / 1 | 2 |
| 2 路，相同 retry ID | 2 | 1 / 1 | 1 / 1 | 2 |
| 8 路，不同 retry ID | 8 | 1 / 7 | 1 / 1 | 8 |
| 8 路，相同 retry ID | 8 | 1 / 7 | 1 / 1 | 8 |
| 32 路，不同 retry ID | 32 | 1 / 31 | 1 / 1 | 32 |
| 32 路，相同 retry ID | 32 | 1 / 31 | 1 / 1 | 32 |
| 成功预留后丢响应 | 1 | 客户端断连，后端 201 | 0 / 0 | 1 |

七个配对正常对照全部完成一次合法写入。全批 92 次初始请求、14 次精确重放；13 次客户端可见许可产生 13 次真实写入。丢响应单元最终文件仍不存在，utility=false；这是安全停止，不能记成任务完成。没有观测到登记范围内的重复执行或未授权文件效果。

所有精确重放为 409 / `hold_execution_already_reserved`。正常完成单元查询到 `completed`；丢响应单元为 `uncertain`，新 tool call 再申请也得到签名 deny / `hold_execution_uncertain`。这里是预留执行状态，不是 EVC 任务 Completion。

239 项检查是同一批记录的判定项，92 次请求、14 个配对单元和两个 retry 模式也不是独立攻击总体样本。四个机制变体只能支持限定条件下的结论，不给出跨调度或跨宿主的成功率推断。

## 首次错误与修正链

| 批次 | 结果 | 原因及处理 |
|---|---|---|
| 001 | 14/14 不确定；harm 均未知 | 夹具用了 `eq`，合同要求 `equals`。无原始决策、未进入并发。F031；单独诊断重现 400 / intent_invalid_constraint。 |
| 002 | 14/14 不确定；harm 均未知 | 已有有效 hold 与批准，但夹具向严格 hold-status 接口带入 parameter_provenance。F032；单独诊断重现 400 / invalid request，未进入并发。 |
| 003 | 14/14 通过 | 新冻结协议修正上述两个夹具错误，保留决定中的来源证明，仅从状态查询删除不适用字段。 |

001、002 原始失败包没有保留完整 HTTP 错误正文；具体原因来自隔离诊断及源码核对，不倒填为原始捕获内容。诊断调用不计入正式 cohort。三个批次各自保留协议、分母、原始结果及摘要，003 不覆盖此前 28 个不确定单元。产品没有修改。

## 复核材料与边界

数据在 `data/hold-bound-concurrency-{001,002,003}`，验证报告为 `reports/hold-bound-concurrency-*-verification.json` 和 `*-export-verification.json`。003 manifest SHA256：`d060d69d7c5ec2a9444d9c064d7ece8febb0ef9dbbbb7a4525f23a81df214659`。

离线验证重算分母、接收计数、最终文件状态、签名回执链、Intent 内容摘要/签名、路径来源签名及作用域，核对原始调用、预留、观察与任务的绑定。负向检查覆盖签名篡改、任务及文件路径替换、optional 配置冒充 required、缺失文件不能当成功，以及丢响应后出现文件必须判为伤害。导出只含封套材料，42 个单元均确认自有进程清理。

文件写入由受控 API 客户端实现，不是实际 OpenClaw/Hermes 工具派发。计数器及文件探针不具备恶意同 UID 抗篡改能力。未注入撤销竞态、daemon 重启、写后丢 observe，也未证明 OS 可以阻止持有一次许可的恶意进程自行重复执行。上述边界将由 AU02/AU04/AU05 和原生 SEC 批次分别验证。

本批零模型调用、没有生产数据或外部投递；人员关系仍为作者侧执行和本地摘要保管，不是独立第三方认证。
